## 0. 口径对齐（先把给定的 6 个数字自洽化）

给定的 6 个数字只有在下列唯一解释下才互相自洽，本文全文采用此解释：

| 给定口径 | 本文解释 | 校验 |
|---|---|---|
| 1亿同时在线 | **大促/极端峰值在线**，不是日常在线 | 见公式 F1 |
| 3亿 DAU | 日活总量，用于反推在线人数 | — |
| 读 300万~500万 QPS | **1亿在线对应的应用层（网关入口）读 QPS 峰值** | 见公式 F2，人均 0.03~0.05 读/秒 |
| 写 50万~100万 QPS | **同口径的应用层写 QPS 峰值** | 人均 0.005~0.01 写/秒 |
| 订单创建峰值 50万笔/s | **大促瞬时峰值**（零点/整点场次），被包含在"写 50万~100万 QPS"之内 | 见 §0.1 的张力说明 |
| 大促系数 5~10x | **大促峰值 ÷ 日常峰值**，因此日常读 QPS = 50万~100万，在线 = 1000万~2000万 | 见 §1.5 |

### 0.1 两个必须点名的口径问题（诚实量化）

**问题 A：`订单创建 50万笔/s` 比公开可参照量级高约 50 倍。**
公开可参照值：双 11 订单创建峰值 ≈ 58.3 万笔/**分钟** ≈ 9,700 笔/s；支付宝支付峰值 ≈ 20.5 万笔/s。
本口径 50万笔/s = 上述值的 ~51 倍。本文**按要求照算**（§1.4 给出它所需的 Pod/分片），但必须同时给出结论：

- 若 50万/s 指**最终成交订单**，则本平台的规模 = 全球电商历史峰值的 50 倍，容量与三方依赖（见 §7）均不可达；
- 若 50万/s 指**下单接口调用次数（含购物车试算、预下单、拆单中间态）**，则最终订单可能只有 5万~10万/s，容量立刻可行。
- **两种口径的容量差异 ≈ 10 倍**（下单 Pod 3,125 vs 312，订单库分片 417 vs 42）。**必须在压测前由业务方书面确认采用哪一种**，否则第 2.5 节的压测目标值无法确定。

**问题 B：写 QPS 口径内部挤压。**
若"订单创建 50万/s"包含在"写 50万~100万 QPS"内，则除订单外只剩 0~50万 QPS 给库存、积分、埋点、评论、日志、消息全部写入 —— 不成立。
**结论：埋点/行为流水/审计日志/搜索索引更新必须走 Kafka → 数仓/ES，不得写 MySQL**（与 `ios-backend.md` 11.6 的 Kafka+Flink 链路一致），本文按此假设计算写 TPS。

## 1. 容量规划模型

### 1.1 公式链（在线 → QPS → Pod → 分片 → 连接 → 线程）

```
F1  在线人数      O = DAU × D × β                    [人·小时→峰值小时并发]
F2  应用层 QPS    Q = O × f                          f = 人均每秒请求数
F3  内部 RPC      R = Q_read × k_r + Q_write × k_w   k = 平均扇出系数
F4  单 Pod 能力   C_pod = (v_cpu × 1000 × U) / c     U=目标CPU利用率, c=单请求CPU成本(ms)
F5  Pod 数        N_pod = Q / C_entry + R / C_rpc
F6  DB 写分片     N_shard = (Q_write × w) / T_inst   w=每请求写行数, T_inst=单实例TPS
F7  DB 连接       N_conn = N_shard × P × 0.7         P=每分片连接预算
F8  线程          N_thr = N_pod × t_pod              t_pod=每Pod工作线程数
F9  带宽          B = Q_read × S_resp                S_resp=gzip后平均响应体积
```

#### F1：从 DAU 反推「1亿在线」是否成立

- 全日在线人时 `H = DAU × D`（D = 日均使用时长）
- 峰值小时在线 `O = H × β`（β = 峰值小时占全天使用量比例）

| 场景 | DAU | D | β | O 峰值在线 |
|---|---|---|---|---|
| 日常晚高峰 | 3亿 | 0.5 h | 10% | **1,500 万** |
| 日常（乐观） | 3亿 | 0.75 h | 12% | **2,700 万** |
| **大促（本口径）** | 3亿 | 1.0 h | **33%** | **9,900 万 ≈ 1亿** |

**结论**：1亿在线要求「人均日使用 1 小时 + 33% 使用量挤在单小时」，这是**零点秒杀/晚会级集中**，只在大促瞬时成立；日常峰值在线按 1,500万~2,700万 规划。这与「大促系数 5~10x」自洽（1亿 ÷ 1,500万 ≈ 6.7x）。

#### F2：QPS 反推（验证给定口径）

`f_read = Q_read / O = 500万 / 1亿 = 0.05 次/s` → 每 20 秒 1 次读请求。

- 主动浏览的 App 实际是每 2~5 秒 1 次 API（f ≈ 0.2~0.5）。
- 给定的 0.05 **只有在 BFF 聚合 + CDN + 推送降频下才成立**（与 `ios-backend.md` 11.1 的 BFF 聚合、11.2 的 CDN 章节自洽）。若不做聚合，读 QPS = 1,500万~2,500万，**全部容量数字 ×3~5**。
- **敏感性**：f 每 +0.01 → 读 +100万 QPS → 应用层 **+833 Pod**（按 §1.3 中位 1.6 Pod/万在线折算）。

> 这是全模型最脆弱的假设，**阶段 1 预压测必须实测真实 f 值并回填**。

#### F4：单 Pod 能力（△ 经验值 + 推导）

| 参数 | 取值 | 依据 |
|---|---|---|
| Pod 规格 | 4 vCPU / 8 GiB | Java 服务标准规格（与 §4.2 堆配置配套） |
| 目标利用率 U | **60%** | 留 40% 给毛刺/GC/重启瞬间，99.99% 必须低水位运行 |
| 每 Pod 可用 CPU | 4 × 1000 × 0.6 = **2,400 ms/s** | — |
| 入口请求 CPU 成本 c_e | **2.0 ms**（读写加权） | 读 1.5ms（验签+鉴权+序列化 3KB+1 次 RPC）／写 6ms（事务+校验+发消息），加权 0.86×1.5+0.14×6≈2.1 |
| 内部 RPC CPU 成本 c_r | **1.2 ms** | 反序列化 + 业务逻辑 + 1 次缓存/DB 访问 |

#### 1.4.3 DB 连接数（模型最容易算崩的一层）

`admin-backend.md` 11.1.1 给出 `maximum-pool-size: 50`，**按 1.6 万 Pod 直乘 = 80 万连接，任何 MySQL 实例都会被击穿**（单实例 `max_connections` 通常 2,000~4,000，且 >4,000 后性能反降）。

正确模型：
```
应用侧理论连接 = N_pod × pool                 (16,000 × 50 = 800,000)  ✗
DB 侧可承受   = N_shard × P × 0.7             (500 × 50 × 0.7 = 17,500) ✓
实际配置       = min(应用侧, DB侧) 必须经 ShardingSphere-Proxy / ProxySQL 汇聚复用
```

| 约束 | 取值 |
|---|---|
| 每分片连接预算 P | 50（读写混合）/ 30（纯写） |
| 安全系数 | 0.7（留出 DBA/监控/备份连接） |
| 应用侧 pool（经 Proxy） | **10~20/Pod**（不是 50） |
| 应用侧 pool（直连分片，仅内网低 QPS 服务） | ≤ 50 |
| **每万在线有效连接** | **2~5** |
| **1亿在线总连接** | **2万~5万**（分摊到 500 主分片 + 从库） |
| 硬上限 | 单 Proxy 集群 ≤ 10万 连接；单 MySQL 实例 ≤ 2,000（`thread_pool` 模式下 500 即可） |

> **必须修正**：`admin-backend.md` 11.1.1 的 `connection-test-query: SELECT 1` 在 JDBC4 驱动下多余，应改为 `validationTimeout=3000`；`maximum-pool-size` 改为**按分片配额下发的变量**，不写死 50。

#### 1.4.4 线程池

```
并发需求  X = QPS × RT(s)                    (Little's Law)
例：单 Pod 1,200 QPS × 0.2s = 240 并发
平台线程  core = min(2 × vCPU, X) = 200      超出部分进队列
队列      capacity = QPS × 可接受排队时间 = 1200 × 0.1 = 120   (超过即拒绝)
拒绝策略  CallerRuns / 快速失败返回 429       —— 保 P99 而非保成功
```

| 指标 | 每万在线 | 1 亿在线 |
|---|---|---|
| 平台工作线程（每 Pod 200） | 200~440 | 200万~440万 |
| 若启用虚拟线程（Java 21） | 平台线程降至 4/vCPU，内存省 90% | 见 §4.5 |

#### 1.4.5 带宽

- 应用层：`B = Q_read × S = 500万 × 3KB(gzip后) = 15 GB/s = 120 Gbps` 出口（**不含图片**）
- CDN：`1亿 × 0.2 图片/s × 80KB = 1.6 GB/s = 12.8 Tbps`（**是应用层的 100 倍**）
- **结论：带宽预算的大头在 CDN，必须提前与 CDN 厂商签带宽 SLA 与回源 QoS，这是采购项不是技术项。**

### 1.6 99.99% 的容量含义（误差预算）

| 项 | 值 |
|---|---|
| 年度错误预算 | **52.6 分钟** |
| 月度错误预算 | **4.32 分钟** |
| 串联衰减 | 全局 `A = ∏ Aᵢ`，`A_i = 0.9999^(1/n)` |
| **n=5 个故障域** | 每域需 ≥ **99.998%**（年故障 10.5 min） |
| **n=10 个故障域** | 每域需 ≥ **99.999%**（年故障 5.26 min） |
| 单组件故障换算 | 每月切换 1 次 × RTO 30s = 6 min/年 = 99.999% ✓ |
| **硬约束 1** | 关键调用链**串联故障域 ≤ 10**，超出必须旁路/降级/合并 |
| **硬约束 2** | 任何单组件 **RTO ≤ 30s、月故障次数 ≤ 2**，否则 99.99% 不可达 |
| **硬约束 3** | 每服务 **≥3 副本、跨 2 可用区**，PDB `minAvailable=2`；单可用区失效需预留 **≥40% 冗余容量** |
| 变更预算 | 计划内变更导致的抖动 ≤ 15 min/年 → 大促期间**变更冻结**，蓝绿/灰度必须秒级可回滚（`admin-backend.md` 16.2 的"错误率>5%自动回滚"需改为 1%，见 §8） |

## 2. 全链路压测

### 2.1 压测目标与总量

| 项 | 目标值 |
|---|---|
| 压测峰值 | **120% × 大促目标 = 读 600万 QPS / 写 120万 QPS / 入口 756万 QPS**（入口按 08 号 630 万上限 ×120%，见 §1.2 收敛注） |
| 订单创建 | **60万笔/s**（= 50万 × 1.2；若口径为 5万/s 则 6万/s，见 §0.1） |
| 持续时长 | 120% 阶梯 15~30 min/级；100% 稳定性压测 ≥ 2 h |
| 验收 | P99 ≤ SLO、错误率 ≤ 0.01%、CPU ≤ 70%、队列无持续增长、无单点 |

### 2.2 流量染色（网关 → RPC → MQ → DB 全链路透传）

**染色标识**：`tc.flag`（0=生产，1=压测），载体为不透明字符串 `stress:<batch_id>:<seq>`，`batch_id` 全局唯一（格式 `pt_YYYYMMDD_HHmmss_xxxx`），**用于压测数据的精确清理与对账**。

```
压测端(打标) 
  │  Header: X-TC-Flag: 1 ; X-TC-Batch: pt_20261011_2000_a1b2
  ▼
网关(唯一入口，强制注入/校验)
  │  校验：压测 token 白名单 + 来源 IP 段；注入 TraceId 前缀 "PT-"
  │  产出：TraceContext{flag, batchId, traceId} → TransmittableThreadLocal
  ├──► HTTP/REST  ── Feign/OkHttp Interceptor 透传 X-TC-Flag
  ├──► gRPC       ── ClientInterceptor / ServerInterceptor 写入 metadata `x-tc-flag`
  ├──► 消息队列   ── MessageProperties `tc.flag` / `tc.batch` （生产端写入，消费端读出重建上下文）
  ├──► 异步线程   ── TaskDecorator + TransmittableThreadLocal（TTL），杜绝 @Async/线程池丢标识
  ├──► 定时任务   ── 批处理按行内 flag 分流（压测批次数据只进影子表）
  └──► DB         ── AbstractRoutingDataSource → 影子 DataSource（见 2.3）
```

**三个最常见漏染色点（必须单测覆盖）**：
1. `@Async` / 线程池 / `CompletableFuture` 上下文丢失 → 强制用 TTL 装饰所有线程池；
2. MQ 消费端拿不到 flag → 消费入口**第一行**重建上下文，未带 flag 的消息按生产处理（fail-safe 方向相反，见 2.4）；
3. 定时任务/延迟消息/回调（支付回调、第三方 webhook）无染色 → 压测期这些入口一律走 Mock 网关。

### 2.3 影子库 / 影子表（数据隔离标识）

| 存储 | 方案 | 标识与路由 | 说明 |
|---|---|---|---|
| **MySQL（分表）** | **逻辑影子表** | `order_main` → `shadow_order_main`；ShardingSphere **Hint 路由** `hintManager.setShardingValue("tc.flag",1)` | 与 `admin-backend.md` 1.2.1 的"单库+按月逻辑分表 + ShardingSphere 透明路由"完全兼容，业务代码零侵入 |
| **MySQL（未分表）** | **影子库** | 同实例 `shadow_<db>` schema，或独立影子实例 | 数据量大时用独立实例，避免压测 IO 影响生产 |
| 影子表命名 | 表名前缀 `shadow_`，**且每张影子表必含 `tc_batch_id` 列**（无主键业务含义，仅供清理/对账） | `idx_batch(tc_batch_id)` | 清理与对账的唯一钥匙 |
| **Redis** | Key 前缀 `shadow:{...}`，或**独立影子集群** | KeyBuilder 统一入口 + 拦截器校验 | 影子 key **强制 TTL = 1h**，天然兜底清理 |
| **Elasticsearch** | 影子索引 `shadow_<index>_v<n>` | IndexNameResolver 按 flag 解析 | 压测完直接 Delete Index |
| **RabbitMQ / Kafka** | 影子 Exchange/Queue：`shadow.order.exchange` / `shadow.order.created.q`；Kafka 用影子 Topic `stress.order.created` | 消费者同时绑定，按路由键前缀分流 | 消费端消费后写影子表 |
| **第三方（支付/短信/物流/APNs）** | **Mock 网关**，按 flag 强制拦截 | flag=1 命中 Mock 而非真实通道 | **红线：压测流量严禁触达真实支付/短信通道** |
| **数据仓库/埋点** | 影子 Kafka Cluster 或 `tc.flag` 分区隔离 | 否则污染数仓与运营看板 | 埋点侧必须按 `batch_id` 标记 |

### 2.4 漏染色防护（fail-fast 三道闸）

```
闸1 DAO 层 MyBatis Interceptor：
     if (flag==1 && SQL 目标表 !^shadow_) throw new ShadowRouteViolationException
     if (flag==0 && SQL 目标表 ^shadow_) throw new ShadowRouteViolationException   ← 反向同样致命
闸2 Redis/ES 客户端拦截器：key/index 前缀与 flag 一致性断言
闸3 运行时监控：shadow_route_miss_total{service,table} 指标 = 0 才允许加压
```

**压测前自检（准入条件）**：
- 「影子空跑」：0 压测流量下先跑 10 分钟，验证 100% 关键接口的染色断言用例全绿；
- **生产表行数增量监控**：压测窗口内，所有业务表 `COUNT(*)` 增量必须为 0（读表行数不变、写表行数不变）；出现任何增量 **立即中止压测**；
- Redis `used_memory`、ES 索引文档数、MQ 队列深度 同口径监控；
- 影子表与业务表**结构同构校验**（Flyway 同一迁移脚本建两份），避免字段不一致导致压测结果失真。

### 2.5 生产环境压测流程（五个阶段）

| 阶段 | 时机 | 内容 | 出口条件 |
|---|---|---|---|
| **T-0 准备** | 随时 | 影子链路改造 + 三道闸 + 自检用例 + 容量模型确认（含 §0.1 口径书面确认） | 自检 100% 通过 |
| **阶段1 预压测（单接口极限）** | T-30 天 | 找**单实例极限 QPS**：逐接口加压至 P99 拐点/错误率 0.1% | **回填 §1.1 F4 的 c 值，校准模型（误差目标 ±20%）** |
| **阶段2 单链路压测** | T-21 天 | 下单链路、支付链路端到端（影子库），找链路瓶颈 | 链路 P99 ≤ SLO × 1.1 |
| **阶段3 全链路压测（生产）** | T-14 ~ T-7 天 | **阶梯加压 30% → 50% → 80% → 100% → 120%**，每级保持 15~30 min；每级之间观察 10 min（看队列是否回落） | 120% 达标 |
| **阶段4 稳定性 + 混沌** | T-7 ~ T-5 天 | 100% 峰值持续 2h（可选 8h）；期间随机杀 Pod、断 1 个可用区、注入下游超时 | 无雪崩、无不可恢复积压 |
| **阶段5 大促前回归** | T-3 天 / T-1 天 | T-3：限流阈值与预案演练（故意触发限流/熔断/降级，验证生效）；T-1：**只读轻量回归**（10% 流量 15 min）+ 缓存/连接池预热 | 全部通过后冻结变更 |

**压测流量怎么产生（诚实说明）**：600万 QPS 用 JMeter/Gatling 纯生成需要 **600万 ÷ 5,000 = 1,200 台压测机**（§1.3 表），不现实。可行方案按优先级：

1. **流量录制 + 回放放大**（推荐）：网关侧录制真实生产流量（tc-dump / GoReplay / mirroring），剥离敏感字段后回放并按倍数放大 → 压测机仅需 **100~300 台**；
2. **影子流量镜像**：生产流量旁路复制到压测集群（1:1），再叠加 3~5x 生成；
3. **纯生成**：仅用于单接口阶段 1（几十台即可）；
4. **历史大促流量回放**：用上一次大促的录制数据，时间轴压缩 5~10x。

> `admin-backend.md` 15.3 只写了「JMeter/Gatling」，**未给目标 QPS 与压测机规模**，必须按本节补齐（见 §8 核验 #15）。

### 2.6 压测数据清理与对账

| 存储 | 清理方式 | SLA |
|---|---|---|
| MySQL 影子表 | `DELETE FROM shadow_xxx WHERE tc_batch_id=?`（大批量分批删，每批 5,000）；整轮压测可 `TRUNCATE` | 压测结束后 **30 min 内完成** |
| MySQL 影子库 | 清空后保留结构 24h，随后 Drop | 24h |
| Redis | 影子 key **TTL=1h 自动过期**（强制）+ 主动 `SCAN shadow:* DEL` | 1h |
| MQ 影子队列 | 消费完自动删除 / 队列 TTL；生产端停止后 drain | 30 min |
| ES 影子索引 | `DELETE shadow_*` | 30 min |
| 数仓/埋点 | 按 `batch_id` 分区 Drop | 2h |
| 第三方 Mock 记录 | Mock 服务侧清理 | 30 min |

**对账（必须做，否则"清了"是自欺）**：
1. 清理后逐表 `COUNT(*) WHERE tc_batch_id=?` = 0；
2. 清理后**业务表**行数 = 压测前基线（快照对比）；
3. 清理任务本身有指标 `shadow_cleanup_rows{batch,table}` 与 `shadow_cleanup_pending`，未归零告警；
4. 压测报告 + 数据快照 + `batch_id` 清单保留 **7 天**，供事故回溯；
5. **清理失败必须阻断下一轮压测**（准入条件之一）。

### 2.7 压测通过标准（验收门禁）

| # | 指标 | 阈值 |
|---|---|---|

## 4. 性能优化清单（按收益/成本排序）

### 4.1 ROI 总排序（收益 = 容量/延迟改善；成本 = 人日）

### 4.2 JVM 调优（4C8G Pod）

```bash
# 堆大小公式：Xmx = 容器内存 × 0.50~0.65
#   留给：Metaspace(~120M) + 线程栈(200×1M=200M) + 堆外/Direct Buffer(RPC 收发) + OS page cache
-Xms4g -Xmx4g -XX:MaxMetaspaceSize=256m -XX:ReservedCodeCacheSize=128m
-XX:MaxDirectMemorySize=1g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=100
-XX:G1NewSizePercent=10 -XX:G1MaxNewSizePercent=25      # 新生代：RPC/JSON 短命对象多
-XX:G1HeapRegionSize=2m                                  # 4G 堆 / 2m = 2048 region（G1 推荐上限）
-XX:InitiatingHeapOccupancyPercent=45                    # 长连接缓存多，提前触发并发周期，避免 Full GC
-XX:+ParallelRefProcEnabled -XX:+AlwaysPreTouch
-XX:+ExitOnOutOfMemoryError -XX:HeapDumpPath=/dump       # OOM 直接退出让 K8s 拉起，避免带病运行
-XX:+HeapDumpOnOutOfMemoryError
```

| 决策点 | 结论 | 依据 |
|---|---|---|
| **分代** | 保留分代（G1 默认分代；JDK 21 ZGC 已分代） | 电商 RPC/JSON 95%+ 是朝生夕灭对象，分代假说收益极高 |
| **GC 选型** | 4C8G 默认 **G1**；堆 >16G 或 P99 <100ms 且分配速率 >2GB/s → **ZGC（JDK 21 分代）**；批处理 → Parallel | G1 吞吐稳、停顿可控；ZGC 停顿 <10ms 但吞吐低 5~15%、堆内存 +5~10% |
| **新生代 vs 分配速率** | YGC 停顿占比 ≈ 分配速率 ÷ 新生代大小；分配 500MB/s、新生代 512MB → 每秒 1 次 × 20ms = 2% 时间。**>2GB/s 分配必须加大 `G1MaxNewSize` 或换 ZGC** | 实测项 |
| **Full GC** | **目标 = 0 次/天**，出现即 P1 缺陷 | — |
| **G1 停顿 SLO** | P99 ≤ 50ms，单次 ≤ 100ms | 否则吃掉下单 800ms 缓冲 |
| **堆使用率** | 稳态 40~70%，>80% 持续 5min 告警 | — |
| **容器感知** | 必开 `-XX:+UseContainerSupport`；K8s `requests=limits=4C/8G`，避免 throttling | CPU throttling 是 P99 毛刺第一来源 |
| **JIT/编译** | 避免频繁滚动重启导致 C2 未编译（解释执行慢 10~50x）→ 预热 30s 再接流量（`preStop sleep` + readiness 探针） | — |

### 4.3 网络与序列化

| 项 | 方案 | 量化收益 |
|---|---|---|
| 连接池 | 客户端↔服务：**每实例 1 个连接池，max 200/实例**，`keepAlive 30s`；禁止每次新建 | TCP+TLS 握手 1~3 RTT 消除（P99 -30~90ms） |
| HTTP/2 | **全链路 HTTP/2**（端→网关、网关→服务、服务→服务 gRPC 天然 H2） | 连接数 -70%，头部压缩 HPACK -30% 字节 |
| 序列化 | **跨语言/内部 RPC → Protobuf**；对外端接口保留 JSON | CPU -15~30%，体积 -50~70%（`ios-backend.md` 11.3 已列"数据压缩"，本文补内部链路） |
| 压缩 | 传输 gzip(6) / **Brotli(5)**，>4KB 才压；图片走 WebP/HEIC（`ios-backend.md` 11.2） | 传输体积 -60~80% |
| 超时 | **分层预算**：端 10s → 网关 10s（`admin-backend.md` 1.1.2 已定）→ 服务 3s → 下游 1s → 单跳 300ms；**每层下游超时总和 ≤ 本层预算** | 消除级联超时雪崩 |
| 重试 | 仅幂等重试（`admin-backend.md` 1.1.2 已定）+ 抖动退避 + **重试预算 ≤ 10%** | 消除重试风暴（典型故障放大 5~10x） |
| DNS/预热 | 端侧 DNS 预解析 + TCP/TLS 预握手（`ios-backend.md` 11.3 已列） | 首请求 -100~200ms |

### 4.4 SQL 治理

| 治理项 | 阈值/规则 | 采集 |
|---|---|---|
| 慢查询定义 | **执行 > 100ms 或 扫描行 > 100,000 或 临时表/文件排序** | `slow_query_log` + `pt-query-digest` + performance_schema |
| 慢查询 SLO | **≤ 5 条/天**（新增慢查询 = 缺陷单） | 每日报告 |
| 全表扫描 | **在线链路 = 0** | 指标 `mysql_global_status_select_full_scan` |
| 分页 | 强制 **keyset 游标**（`id > last_id ORDER BY id LIMIT n`），禁止深 `OFFSET`；`pageSize ≤ 100`（`admin-frontend.md` 16.4 已定）| 拦截器校验 |
| 索引 | 单表索引 ≤ 5；覆盖索引优先；禁索引列函数/隐式转换；联合索引最左前缀 | Schema 评审 |
| SQL 形态 | 禁 `SELECT *`；禁无 `LIMIT` 查询；批量 IN ≤ 1,000 | MyBatis 拦截器 |
| 分表阈值 | **单表 > 5,000 万行** 或 磁盘 IO > 70% 持续 5min → 触发分库（与 `ios-backend.md` 11.4、`admin-backend.md` 1.2.1 一致） | 每日巡检 |
| 连接 | 见 §1.4.3；`maximum-pool-size` 由分片配额下发 | Hikari 指标 |
| 读写分离 | 库存扣减/支付回调/写后读 → **强制主库**；其余读走从库 | 路由注解 |
| 事务 | 在线事务 ≤ 300ms；禁止事务内 RPC/发 MQ（本地消息表替代，`admin-backend.md` 13.2.1 已定） | 慢事务告警 |

### 4.5 线程池治理

| 规则 | 要求 |
|---|---|
| 禁止 | `Executors.newFixedThreadPool / newCachedThreadPool / newSingleThreadExecutor`（无界队列/无限线程 → OOM） |
| 必须 | 显式 `core / max / queueCapacity / RejectedExecutionHandler` + 业务命名 `order-create-pool` |
| 容量公式 | `core = min(2×vCPU, QPS×RT)`；`queue = QPS×可接受排队时间`；超出**快速失败**（返回 429），不无限等待 |
| 隔离（舱壁） | **每下游依赖一个独立小池**：`pool-price`、`pool-inventory`、`pool-promotion`，防单一下游拖垮全部 |
| 池分类 | CPU 池（=vCPU）与 IO 池分开；定时任务单独池（防业务线程被占） |
| 监控 | 每池 `active/max`、`queue_size/capacity`、`rejected_total`，三者均进 §6 触发阈值 |
| 虚拟线程 | Java 21 IO 密集服务启用；**同步锁内不做 IO**（避免 pinning）；CPU 密集仍用平台线程池 |
| 上下文 | 全部线程池用 **TransmittableThreadLocal** 装饰（§2.2 染色透传的硬前提） |

### 4.6 异步化

**同步链路最小化原则**：下单同步只做「验价 + 库存预扣 + 订单/明细/幂等落库 + 本地消息表」，以下全部转 MQ 最终一致（`admin-backend.md` 13.2.1 本地消息表已定方案）：

积分发放、优惠券回填、推荐特征更新、ES 索引、站内信/推送、短信、看板统计、埋点、对账记录、物流预分配。

| 指标 | 同步全做 | 异步化后 |
|---|---|---|
| 下单 P99 | ~1,500 ms | **800 ms（§3.3）** |
| MySQL 写 TPS | 100% | **≈50%**（→ 分片数减半，见 §1.4.2） |
| 扇出 k（写） | 8~10 | **6**（→ 内部 RPC -25%） |
| 代价 | — | 最终一致（≤ 5 min 补偿，`admin-backend.md` 14.2 每 5 min 对账） |

**请求级并行**：BFF 用 `CompletableFuture.allOf` + 每子调用独立超时 + 降级返回（`ios-backend.md` 11.1、`android-backend.md` 12.1 已约定"下游超时返回空数组 + degraded 标记"），**并行后取 max 而非 sum**（§3.3 首页 60ms 即 max 分支）。

## 5. 热点与瓶颈治理

### 5.1 热点探测流程（6 步闭环）

```
① 采集（1s 窗口）
   网关层：按 (path + 参数指纹) 聚合 Top-K；  Redis 代理层：按 key 聚合 QPS
   应用层：本地缓存命中率突增、单 key 访问计数（Count-Min Sketch / 精准 Top-K）
   DB 层：单行 UPDATE 频次、单索引扫描量
② 判定阈值
   L1 key 热点：单 key QPS > 10,000（占单 Redis 分片 10% 容量）
   L2 行 热点：单行写 > 100 次/s（库存行、账户余额行）
   L3 商品级：单 SPU 访问 > 50,000 QPS（秒杀/爆款）
③ 分级响应
   L1 → 本地 Caffeine 缓存（TTL 1~5s）+ 广播预热所有实例
   L2 → Redis 预扣 + 异步落库 + **库存分段**（1 个 SKU 拆 N 段，N = 目标QPS/10万）
   L3 → 独立 Redis 集群 + 前端静态化/排队 + 令牌桶
④ 治理落地 → ⑤ 压测复现验证（P99 回落确认）→ ⑥ 沉淀为预案与白名单
```

**大促预热（T-1 天）**：按历史与预约数据取 **Top 1 万 SPU**，预热 ①本地缓存 ②Redis ③CDN 图片 ④ES 热分片；预热完成度作为压测准入条件之一（`admin-backend.md` 11.2.2 已列缓存预热，本文补"按预测 Top-K"与完成度门禁）。

**三类经典热点的既有对策核验**（与 `ios-backend.md` 1.4.6 一致，均为正确方案）：穿透 → 布隆 + 空值缓存；击穿 → 互斥重建 + 逻辑过期 + 热 key 不过期；雪崩 → TTL ±10% 抖动 + 多级兜底。**缺的是"探测"环节，本文补齐。**

#### 5.2.2 限流阈值设定（公式，不是拍脑袋）

```
① 单实例阈值 = 压测实测极限 QPS × 0.7        （留 30% 给毛刺与长尾）
② 服务阈值   = 单实例阈值 × 实例数 × 0.8     （留 20% 给重启/滚动发布）
③ 入口总闸   = min( 后端总容量 × 1.1,
                    最弱下游依赖容量 × 0.9,
                    第三方配额 × 0.8 )        ← 第三方配额通常是真正瓶颈
④ 用户级     ：写接口 10 次/min/用户，读 60 次/s/设备，秒杀 1 次/s/用户
⑤ 算法       ：读 → 令牌桶（rate=阈值，burst=2×rate）；写 → 单机固定窗口（省 Redis 依赖）
                秒杀 → 令牌桶 + 服务端排队（队列容量 = rate×2s，超出返回"排队中"）
⑥ 熔断       ：10s 窗口，样本 ≥20 且错误率 ≥50% → OPEN；30s 后半开放 5 个试探
⑦ 降级白名单 ：可降级（推荐/配置/未读数→0/图片占位）；禁止降级（下单、支付、退款、结算 —— admin-backend 1.1.2 口径正确，保留）
```

**注**：`admin-backend.md` 11.4 只给了 Sentinel 配置骨架，**未给任何阈值** → 全部以本节公式 + 阶段 1 实测值填充（见 §8 #5）。

## 6. 容量触发指标（什么指标到多少就扩容）

### 6.1 触发阈值表（三层：预警 / 扩容 / 紧急）

| 资源 | 预警（观察） | **扩容触发** | 紧急（预案） |
|---|---|---|---|
| **应用 CPU** | 50% 持续 5min | **60% 持续 5min** | 75% 持续 3min |
| 应用内存 | 70% | 80% 持续 5min | 90% |
| **接口 P99** | > SLO×1.2 持续 5min | **> SLO×1.3 持续 5min** | > SLO×2 或 P99.9 > SLO×3 |
| 错误率 | 0.1% | **0.5% 持续 3min** | 1%（触发自动回滚，见 §8 #3） |
| 线程池活跃率 | 70% | **80% 持续 5min** | 95% 或拒绝数 > 0 持续 1min |
| 线程池队列深度 | > 50% 容量 | **> 70% 持续 3min** | 95% |
| 连接池（Hikari）usage | 60% | **70% 持续 5min**；`pending > 0` 持续 1min | 85% |
| 入口 QPS | > 容量×0.7 | **> 容量×0.8 持续 5min** | > 容量×0.9（同时触发限流） |
| **DB 实例 TPS** | > 单实例×0.5 | **> ×0.6 持续 5min** | > ×0.75 |
| DB 连接使用率 | 60% | **70%** | 85% |
| DB 主从延迟 | 500ms | **1s 持续 3min** | 5s（写后读强制切主） |
| DB 慢查询 | > 5/min | > 20/min | > 100/min |
| 磁盘使用率 | 60% | **70%** | 85%（扩容/清理/归档） |
| **Redis 内存** | 60% | **70%** | 85%（触发扩容或淘汰策略审查） |
| Redis 单分片 CPU | 50% | **60% 持续 5min** | 75% |
| Redis 命中率 | < 92% | **< 90%** | < 80%（穿透/雪崩嫌疑） |
| **MQ 消费积压** | > 30s 消费量 | **> 60s 持续 3min** | > 300s 或堆积曲线单调上升 15min |
| MQ 消费延迟 | 5s | **10s** | 60s |
| ES 拒绝/排队 | > 0 | 拒绝率 > 0.1% | > 1% |
| 热 key（§5.1 L1） | > 5,000 QPS/key | **> 10,000** | > 50,000（立即本地缓存 + 排队） |
| 错误预算 | 月消耗 30% | **月消耗 50%（冻结发布）** | 100%（全员复盘） |

### 6.2 扩容响应时间目标

| 扩容类型 | 目标 | 构成 |
|---|---|---|
| **自动（HPA）** | **90~120 s 生效** | 指标采集 30s + 判定 30s + 调度 15s + 镜像已预热 5s + 启动 10s + readiness 15s + **缓存预热 30s** |
| **紧急手动** | **≤ 5 min** | 镜像已在节点池、预热脚本就绪，仅改 `replicas` |
| **预测性（计划内）** | **T-7 天完成** | 见 §5.2.1；`10 万 vCPU` 采购需 **T-30 ~ T-90 天** |
| **缩容** | 滞后 **15 min**，每次 ≤30%，间隔 ≥10min，**高峰禁缩** | 防抖，避免抖动式扩缩 |

**必须诚实说明的约束**：
1. **HPA 只能吸收 ≥3 min 周期的波动**（采集+判定+冷启动 ≈ 2 min），**零点秒杀的秒级尖峰 HPA 根本来不及**——因此 **100% 靠预扩容**，HPA 只处理 ±30% 的日常波动；
2. **MySQL 分库、Redis 分片在线重分片不是分钟级**（§6.3），必须提前；
3. 弹性余量：**集群可调度余量常驻 ≥20%**，否则 HPA 拉不动 Pod，等价于无弹性。

### 6.3 中间件扩容的特殊约束（与应用不同）

| 中间件 | 能否在线扩 | 时间 | 结论 |
|---|---|---|---|
| 应用 Pod | ✅ 秒级 | 90~120s | HPA 可用 |
| **Redis Cluster** | ✅ 可在线 reshard | **30~60 min**（迁移 slot + 数据拷贝） | 大促前 7 天完成；**不可当天扩容** |
| **MySQL 分库** | ❌ **不能在线加库**（需重新分片迁移） | **天~周级** | **触发阈值必须早**：单表 2,000 万行预警 / 5,000 万行强制；单实例写 TPS > 60% 持续 5min |
| ES 分片 | ✅ 可扩节点，分片重平衡 | 小时级 | 大促前完成 |
| MQ (Kafka) | ✅ 加 broker + 分区迁移 | 小时级 | 分区数只能增不能减 |
| 网关 Pod | ✅ 秒级 | 90~120s | — |

## 7. 技术上限（本方案的物理上限，以及超出需要什么）

| # | 上限 | 本方案数值 | 超出需要什么 |
|---|---|---|---|
| 1 | **单 Pod 应用能力** | 1,200 QPS（4C8G，60% 利用率）；下单 160 QPS | 水平扩展本无上限，但受下面 2~9 项约束 |
| 2 | **MySQL 单实例** | 4,000~8,000 TPS（强持久化 + ROW binlog + 3~4 二级索引 △）；分片数上限约 **1,000~2,000**（Proxy 连接数、运维复杂度、跨片路由成本） | **超出 2,000 分片** → 需要：① TiDB/OceanBase 类分布式 NewSQL（放弃自建分片运维）② 或数据冷热分层（在线只留 90 天热数据）③ 或按业务拆多套独立 DB 集群（订单/商品/用户各 1,000 分片） |
| 3 | **消息队列（RabbitMQ）** | 镜像队列单节点 2万~5万 msg/s，单集群实战 ≈ **50 万 msg/s**。本方案需 **75万~150万 msg/s** → **超出 1.5~3 倍，RabbitMQ 选型不可达** | **必须换**（对 `admin-backend.md`/`ios-backend.md` 选型的强制修正建议）。**基线裁决（00-conflict-register C2）：替换目标为基线 RocketMQ 5.x**——`04` 号已双路径验证需求 **300 万条/s（设计 350 万）**，需按业务域拆 4~6 个集群（≈175 台）；本文下方"Kafka 25 broker"数字仅作吞吐参照，Kafka 仅用于日志/埋点管道 |
| 4 | **Redis 客户端连接** | 1.6 万 Pod × 每 Pod 连全部 100 分片 = 160 万连接 → **不可行** | ① **按业务域拆 8~12 个独立集群**（每集群 16~32 分片，每 Pod 只连 1~2 个集群），或 ② 引入代理层（Twemproxy/自研，单代理 10万 QPS → 100~150 代理）；16,384 slot 也限止单集群分片数（工程上限 ≈ 200~500 分片） |
| 5 | **Elasticsearch** | 60 万搜索 QPS 需 100~200 数据节点；**200+ 数据节点是自建 ES 的运维上限**，且单分片 ≤50GB（`admin-backend.md` 11.3.1 ✓） | 分域多集群（类目分组各一套）、搜索结果多级缓存（首屏 60% 走缓存）、或**自研/商业搜索引擎**；再高则搜索降级为"热搜词 + 类目导航"模式 |
| 6 | **网关 / LB** | 单 LB（云 SLB）上限 ≈ 500万 QPS / 50 Gbps；七层 TLS 卸载是 CPU 瓶颈 | 多 LB + DNS/Anycast 分流 + 分层（L4 LB → L7 网关），网关 250+ Pod 分集群（按端拆：iOS/Android/Web/Admin 各一集群） |
| 7 | **第三方通道（真正的硬上限）** | 支付宝/微信单商户 QPS 配额通常 **3,000~10,000/s**；短信 1,000 条/s/通道；APNs 连接与速率受限 | **50万/s 支付不可能同步完成** → 必须：① 收银台**排队 + 分批提交** ② 多通道分摊 ③ 大促优先站内信/推送（`ios-backend.md` 6.3.3 已有推送降级为站内信的预案 ✓）④ 与通道方签大促扩容协议（提前 30 天报备峰值） |
| 8 | **单点 ID 生成** | 雪花 41bit 毫秒 + 12bit 序列 = **4,096/ms/机器号 ≈ 410 万/s/机器号** → 50万/s 订单 ID 只需 1 个机器号 | **ID 不是瓶颈**；风险是**时钟回拨** → NTP 硬约束 + 回拨拒绝 + 机器号 ≥64 预留。注意分表后唯一索引仅片内生效，全局唯一靠编码规则（`admin-backend.md` 1.2.1 约束 5 ✓） |
| 9 | **可用区/单地域容量** | 单地域合理上限 ≈ **5 万~8 万 vCPU**（受机房电力、单 AZ 故障半径、交换机规模限制）；本方案 10 万 vCPU **已超出单 AZ** | ① **单地域双/三可用区**（本方案必需，见 §1.6）② 超过 ~5,000 万在线 → **异地多活 + 单元化**（按用户分片路由，单元间数据隔离 + 跨单元只读同步），这是从 1 亿走向更高规模的**架构级分水岭** |
| 10 | **CDN 带宽** | 6~19 Tbps、百万级图片 QPS | 提前 30 天与 CDN 厂商签**大促带宽保障 SLA + 回源 QoS**；热点静态资源 T-1 预热；**这是采购/商务项，不是技术项** |
| 11 | **监控/日志吞吐** | 1.6 万 Pod × 平均 2,000 日志行/s = 3,200 万行/s | ELK 不可行 → 需 Kafka + 采样（错误 100%、成功 1%）+ 对象存储冷存；指标侧 Prometheus 分片（Thanos/Mimir）；**全量 Trace 在此规模不可行 → 按 1% 采样 + 错误全采** |
| 12 | **压测流量生成** | 纯生成需 1,200 压测机（§1.3） | 流量录制回放（§2.5），压测机降至 100~300 台 |

**总结一句话**：本方案在 1亿在线口径下的**真正天花板不是计算资源（花钱可解），而是「MySQL 分片运维上限、RabbitMQ 吞吐上限、第三方通道配额、单地域故障半径」四项**；突破它们分别需要：分布式 NewSQL / Kafka / 支付排队削峰 / 异地多活单元化。

### 8.2 核验结论（Top 5 必须修的不现实指标）

1. **`ios-backend.md` 13.5「压测目标 QPS 10000+」** —— 与 1 亿在线口径差 550 倍，必须改为 756 万 QPS（或标注为单服务口径）。**这是最严重的一条，因为它会让整个压测通过一个毫无意义的门槛。**
2. **`ios-backend.md` 11.5「P0 可用性 99.95%」** —— 单项即击穿全局 99.99%（4.38h vs 52.6min 预算），必须 ≥99.99%，P2 必须定义为不计入。
3. **`admin-backend.md` 11.1.1「连接池 50」** —— ×1.6 万 Pod = 80 万连接，必须改为经 Proxy 汇聚的 10~20/Pod + 分片配额。
4. **`admin-backend.md` 12.2 / 16.2「错误率 5% 才告警/回滚」** —— 在 500 万 QPS 下 5% = 1,500 万次失败/分钟，必须提前到 0.5%/1%，并补饱和度告警。
5. **订单创建 50万笔/s 的口径未定义** —— 含与不含其他写入导致容量差 10 倍；且与第三方支付配额（3,000~10,000/s）冲突，必须先确认口径、再排队削峰。
