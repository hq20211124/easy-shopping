# 02 · 数据存储架构（目标 1 亿同时在线）

> **定位**：电商平台数据存储层的容量测算、分布式数据库选型、分片策略、冷热归档、跨服务一致性与落地路径。
> **必读输入**：`plans/admin-backend.md` 1.2（数据库设计与分库分表约束，v1.1 的 5 条落地约束）、`plans/miniprogram-backend.md` 1.4 与 10.5.2（16 库 64 表、扩展表同片约束）。
> **本文口径**：沿用现有表命名（`order_main` / `admin_order_*` / `user_phone_bind` / `payment_order` / `user_footprint` 等），不新造同义表名。

## 0. 统一口径与基准假设

| 指标 | 取值 | 来源/推导 |
|---|---|---|
| 峰值同时在线 | 1 亿 | 给定 |
| DAU | 3 亿 | 给定（同时在线/DAU ≈ 0.33，符合电商早晚高峰曲线） |
| 注册用户（累计） | 10 亿 | 3 亿 DAU / 0.3 = 10 亿，电商注册渗透率 30% 属常规 |
| 订单创建峰值 | 50 万笔/秒 | 给定（双 11 开场级别，阿里 2020 实测 58.3 万笔/秒） |
| 订单年增 | 100 亿行/年（`order_main`） | 给定；与 `01` 号 §0.1"5 亿 MAU × 10 单/年 = 50 亿单/年"并存 → **收敛取 100 亿行/年为规划上限（最保守），50 亿为下限口径**（00-conflict-register C10-k） |
| 日均订单 | 1e10 / 365 = **2740 万单/天** = **317 单/秒** | 计算 |
| 峰值/日均比 | 500000 / 317 ≈ **1578×** | 计算。参照天猫双 11（日常约 400 单/秒、峰值 58.3 万单/秒 ≈ 1450×），该比值**真实可信**，不是口径错误 |
| 单均购买件数 | 1.6 件/单 | 行业经验值（1.4～1.9），用于推 `order_item` |
| 每单平均写行数 | **4.6 行/单** | 见 §1.1 明细（order_main 1 + order_item 1.6 + payment_order 1 + order_status_log 0.7 + 本地消息 0.3） |
| 峰值行写入 | 50 万 × 4.6 = **230 万行/秒** | 这是本方案的**设计写上限**，不是常态 |
| 应用层读 QPS | 300 万～500 万 | 给定 |
| 分片键 | `user_id`（订单/用户域）、`spu_id`（商品域） | 给定，与 admin 1.2.1、miniprogram 10.5.2 一致 |
| 主选/备选/非核心 | OceanBase（主） / TiDB（备） / MySQL（非核心） | 给定 |

**关键结论前置**：

1. 50 万笔/秒**不可能**以同步事务形式落库（任何单库都不行），必须「下单异步化 + 批量落库」把 DB 峰值写平滑到 **20～40 万行/秒**，这决定集群规模。
2. 读 500 万 QPS 不是 DB 的压力，**缓存命中率 ≥95% 才是前提**；DB 实际承接 15～25 万点查/秒。
   > **口径收敛（00-conflict-register C10-d）**：本文"命中率 ≥95% / DB 承接 15~25 万"与 `03` 号"下穿 10% 但经五级收敛后 DB 实际承接 2.4%（12 万@500 万读）"、`08` 号"命中 96% / DB 读 26 万@617 万读"口径不同但不矛盾——03 号把布隆/热点回填/ES 预计算也计入"非 DB 承接"。**统一口径：DB 点查承接规划按 12 万~26 万区间取上限 26 万校验（08 号），缓存综合命中率以 03 号三层定义为验收标准**。
3. 100 亿行/年 × 3 年 = 300 亿行在线+历史，**MySQL 物理分表路线在历史库需要 2 万+ 张物理表**，这是选 OB 的最硬理由（§2.5 有算式）。

## 2. 分布式 DB 选型对比

### 2.1 评分维度与结论

| 维度 | OceanBase | TiDB | 自建 MySQL 分库分表（ShardingSphere） | 权重 |
|---|---|---|---|---|
| **峰值 TPS（50 万单/秒 → 230 万行/秒，削峰后 20～40 万行/秒）** | ✅ 强。多副本 + LSM 分区表，42 observer 可承载 35～49 万行/秒稳定写（批量写增益 1.4×）；批量 INSERT 吞吐随批量增大近线性 | ✅ 强。TiKV Raft 写吞吐与 OB 同量级，但写放大（Raft + RocksDB compaction）通常高 20%～40%，P99 更抖 | ⚠️ 单主写。16 库 × 单库 3～5 万行/秒 = 48～80 万行/秒理论值，但主从延迟、备份、DDL 都要吃掉，实际峰值可用约 50% | 25% |
| **跨片查询** | ✅ 原生。单表 + 分区，SQL 直接 `WHERE store_id=? AND created_at BETWEEN`，优化器自行裁剪分区 | ✅ 原生。同上 | ❌ 最弱。必须靠 **ES/宽表/异构索引**兜底，业务代码要写两套查询路径 | 20% |
| **扩容/rehash** | ✅ 自动。分区在线 split/merge + 自动负载均衡，**应用零改** | ✅ 自动。Region 自动调度，scale-out 分钟级 | ❌ 最痛。预分桶/双写/迁移/校验/切流，需专门团队 + 停写窗口 | 15% |
| **单表行数上限** | ✅ 分区表无 5000 万限制，单分区控制在 5000 万内即可 | ✅ 同上 | ❌ 单物理表 5000 万行红线；历史 3 年 + 1024 分片 = **2.4 万张物理表**（§2.5） | 10% |
| **生态（Spring Boot / ShardingSphere / Canal / 现有 SQL）** | ✅ MySQL 协议兼容，MyBatis/ShardingSphere/Canal 直连可用；OMS 迁移工具成熟 | ✅ MySQL 协议兼容，生态最接近 MySQL，Canal/DTS 支持最好 | ✅✅ 最好。零学习成本，人才最多 | 10% |
| **运维成本** | ⚠️ 中。OB 的 Observer/Zone/租户模型有学习曲线；公有云托管（OCP）降低门槛 | ✅ 中低。TiUP 运维简单，社区文档好 | ❌ 高。16 主 + 32 从 = 48 实例的备份/DDL/主从/切换，**至少 3 名 DBA**，50 万/秒下这是致命的 | 10% |
| **双 11 验证** | ✅✅ 最强。蚂蚁双 11 账户体系、支付宝交易核心长期运行，国产分布式 DB 中双 11 战绩最硬 | ✅ 部分。有头部互联网生产案例，但**金融级核心交易的双 11 保底记录少于 OB** | ⚠️ 分片中间件 + MySQL 的双 11 案例多（阿里自研当年即是），但依赖自研中间件成熟度，**开源 ShardingSphere 未经历过 50 万/秒级别验证** | 10% |

### 2.2 结论

**主选 OceanBase**，理由按权重排序：

1. **跨片查询原生能力**（权重 20%，且是本项目最高频的改造痛点）：商家按 `store_id` 查订单、运营按状态+时间查订单，OB 直接 SQL 即可；MySQL 分片路线必须额外建 ES 索引 + 宽表 + 回表点查三套东西（§3.4）。
2. **扩容不需要 rehash**（15%）：分片数从 2048 → 4096 是 DB 内部动作，ShardingSphere 路线要专门做一轮双写迁移（§3.3）。
3. **单表行数无上限**（10%）：历史 3 年 300 亿行，OB 一张 `order_main` + 2048 分区即可；MySQL 路线要 2.4 万张物理表。
4. 写吞吐与双 11 背书（合计 35%）持平或优于 TiDB。

**备选 TiDB** 的启用条件：OB 授权/商务成本超出预算，或团队已有 TiDB 运维积累 → TiDB 与 OB 在**本文所有架构设计（分片键、路由、CQRS、归档）上可无缝替换**，仅需把 §3.3 的 rehash 方案由"OB 自动分区"改回"预分桶迁移"。**架构文档对二者通用**，不绑定专有 SQL。

**MySQL 的角色**：仅保留给**非核心数据**（§1.5 清单：`admin_*` 配置字典、`admin_data_db`、`user_message`、`admin_reconciliation_*`、`admin_operation_log` 6 个月），单库 2～3 实例，不参与分片。

### 2.3 能力边界（诚实说明）

- OB/TiDB **解决的是"存储与扩展"，不是"跨片事务的免费"**：跨分片分布式事务 RT 是本地事务的 3～8 倍，且占用更多日志带宽。所以下单链路必须按 `user_id` 聚合到同分区，**禁止在下单主事务里跨 `spu_id` 更新商品表**（§5）。
- OB/TiDB **不能替代 ES**：多条件全文检索（关键词、拼音、相关性排序）仍由 `admin-search` 的 ES 承担；OB 只做**精确条件 + 范围条件**的列表查询。
- 二者都**不解决读 QPS**：500 万 QPS 必须靠缓存（§6），指望 DB 直扛是错误设计。

### 2.4 数字校验：OB 在线核心集群规模

| 项 | 计算 | 结果 |
|---|---|---|
| 容量需求 | 71.9 TB 逻辑 × 0.55 压缩 × 3 副本 = 118.6 TB 物理 ÷ (8 TB × 70% 可用/节点 = 5.6 TB) | **21.2 节点**（仅容量） |
| 写需求 | 目标 40 万行/秒 ÷ 2.5 万行/秒/分区组 = 16 个分区组 × 3 副本 = 48 节点裸值 ÷ 1.4（批量写增益） | **35 节点**（仅写，**写是绑定约束**） |
| 读需求 | 25 万点查/秒 ÷ 4 万 QPS/节点 | **7 节点**（仅读） |
| 三机房容灾 | 3 Zone × N 节点，每 Zone ≥ 2 节点，分区分布跨 Zone | 兜底约束 |
| **合计取整** | max(容量 21, 写 35, 读 7) + 20% 水位余量 + 双 11 弹性 | **42 个 observer（3 Zone × 14），24C/128G/8TB NVMe** |

→ 对应 §6 的物理上限：**71.9 TB 在线数据 + 40 万行/秒写 + 160 万点查/秒**，水位 55%～65%，留出双 11 与故障降级空间。

### 2.5 反证：为什么不用 MySQL 分库分表承载"在线 1 年 + 历史 3 年"

```
在线 1 年订单 = 1e10 行
历史 3 年（含在线）= 3e10 行

方案 A：16 库 × 每库 64 表 = 1024 分片（沿用 miniprogram 10.5.2「16 库 64 表」口径）
  单片/年 = 1e10 / 1024 = 976 万行          ✅ < 5000 万红线
  单片/3年 = 3e10 / 1024 = 2.93 亿行        ❌ 超红线 5.9 倍
  → 历史库必须再按月分表：1024 × 36 月 = 36,864 张物理表
  → 单片/月 = 81 万行，表过碎，元数据/备份/DDL 开销反超收益

方案 B：64 分片（16 库 × 每库 4 表，另一种「64 表」解读）
  单片/年 = 1.56 亿行                        ❌ 超红线 3.1 倍
  → 必须 64 × 12 = 768 张月表，单片/月 130 万行 ✅
  → 3 年 = 64 × 36 = 2304 张月表            ✅ 可接受

方案 C（OB 主选）：order_main 单表 + HASH(user_id) 2048 分区 + RANGE(created_at) 月分区
  单分区/年 = 1e10 / 2048 = 488 万行         ✅ < 5000 万
  单分区/3年 = 1.46 亿行（月分区后 406 万）  ✅
  物理表数量 = 1 张                          ✅ 归档 = DROP/EXCHANGE PARTITION（秒级）
```

**结论**：MySQL 路线只有在**放弃"历史 3 年在线可查"**（压缩到 1 年，归档即冷存）时才可行（方案 B + 按月，768 张表）。既然产品要求历史订单 3 年可查、且要求 50 万/秒峰值，**OB 是唯一同时满足三者的选项**。

## 3. 分片策略

### 3.1 分片总则

| 域 | 分片键 | 分片函数 | 分区数 | 跟随表（必须同片） |
|---|---|---|---|---|
| 订单/交易 | `user_id` | `slot = crc32(user_id) % 2048`（OB 为 HASH 分区数 2048） | 2048 | `order_main`、`order_item`、`order_status_log`、`payment_order`、`miniprogram_order_extra`、`refund_order`、`admin_after_sale`、`cart_item`、`user_message`、本地消息表 |
| 用户 | `user_id` | 同上（与订单同片，避免用户+订单跨片） | 2048 | `user`、`user_address`、`user_favorite`、`user_coupon`、`user_points_log` |
| 商品 | `spu_id` | `crc32(spu_id) % 512` | 512 | `product_spu`、`product_sku`、`admin_product_spu_*`、`miniprogram_product_config`、`product_review` |
| 库存 | `sku_id`（即 `spu_id` 派生） | 同商品域 | 512 | `admin_inventory`、`admin_inventory_log_*`（跟随 SKU，不跟随仓库） |
| 商家视图 | `store_id` | `crc32(store_id) % 1024`（**仅宽表用**） | 1024 | `order_store_wide` |
| 全局唯一索引 | 见 §3.5 | — | — | `user_phone_bind`、`user_unionid_mapping` 独立成索引表 |
| 非核心 MySQL | 不分片 | 单库 | — | `admin_*` 配置、结算、对账、日志 |

**分片数为什么是 2048 / 512**：
- 订单：单分区/年 = 488 万行 < 5000 万红线，且 2048 是 2 的幂，取模路由与 OB HASH 分区都高效；扩到 4096 只需在线 split。
- 商品：15 亿 SPU / 512 = 293 万行/分区，量级小，512 已给足 3 年余量（15 亿 → 5 亿在售，商品域增长慢）。
- **`admin-backend.md` 1.2.1 要求"新增表必须先确定它跟随哪张主表分片"** → 上表是强制清单，代码评审必查项。

**必须遵守的既有约束（沿用，不重复造）**：
- admin 1.2.1 约束 1：分片表主键 `BIGINT` + 雪花，**禁止 AUTO_INCREMENT**。
- admin 1.2.1 约束 3：`order_item` / `order_log` 与订单同片。
- admin 1.2.1 约束 5：`uk_order_no` / `uk_spu_code` 等唯一索引仅片内有效，**全局唯一靠编码规则**。
- miniprogram 10.5.2：`miniprogram_order_extra`、`payment_order`、`refund_order`、`cart_item`、`user_message` 同库同分片键。

### 3.2 `order_no` 编码（24 位，定长，可反解路由）

```
order_no = yyyyMMddHHmmss (14) + SSSS 分片槽位 (4) + NNNNNN 序列 (6)
           └──── 时间 ────┘     └ 0000~8191 ──┘   └ 000000~999999 ┘

示例：  20261011153012 + 0417 + 000483
        └ 时间戳 ────┘  └槽位┘ └ 序列 ─┘
```

| 要求 | 设计如何满足 |
|---|---|
| **全局唯一** | 时间 + 槽位 + 序列三段无交集；单秒全局最多 100 万（6 位），单槽位 50 万/8192 = 61 单/秒 ≪ 99 万，**余量 1.6 万倍**（admin 1.2.1 约束 5 的落地实现） |
| **反解路由** | `槽位 = order_no[14:18]`，查「槽位 → 物理分区」映射即可定位，**无需重算 `crc32(user_id)`**；生成器在下单时已知 `user_id`，算出槽位写入 |
| **趋势递增** | 前 14 位是时间 → 主键/二级索引近似顺序插入（B+ 树减少页分裂；OB LSM 下同样利于压实） |
| **分片扩容兼容** | 4 位十进制支持到 **9999 槽**（8192 桶预留 1.2 倍；如需更多可升位到 5 位共 25 位单号）；扩到更多分区时仅「槽位→分区」映射表变化，**历史 order_no 依然可反解**（映射表按槽位版本化，`v1: 0000-8191 → 8192 桶`） |
| **对外展示** | 24 位无字母，客服/用户输入友好；`after_sale_no`、`settlement_no`、`withdraw_no` 复用同一编码（前缀位段替换为业务位） |
| **订单 ID（雪花）** | `id` 与 `order_no` 分离：`id` 用于内部 JOIN/外键，`order_no` 用于对外；两者**都**携带时间高位，可互相校验 |

> 与 `admin-backend.md` 1.2.1 约束 2 的差异说明：原文写 `yyyyMMddHHmmss + 雪花尾段`。雪花尾段**不携带分片信息**，反解路由仍需 `user_id`，与"商家按 order_no 查单"冲突。**本方案改为显式 4 位槽位**，是对原约束的修正，需回写 admin 1.2.1。

### 3.3 扩容与 rehash 方案

#### 3.3.1 OB 主路线：不需要 rehash

```
扩容动作： ALTER TABLE order_main SUBPARTITION SPLIT ...  （或 OCP/OBD 上的在线分区分裂）
数据搬迁： OB 自动在 Zone/节点间搬分区副本，流量按阈值限速
应用感知： 0（路由不变，SQL 不变，连接串不变）
```
- 触发阈值：单分区 > 1500 万行、或单节点 CPU 持续 > 60%、或磁盘水位 > 65%。
- 限速：`sysbench` 级别搬迁限速 ≤ 50 MB/s，避开 20:00～24:00 高峰。
- 回滚：分区分裂是元数据级操作，可回滚；搬迁中可暂停。

#### 3.3.2 MySQL/预分桶路线（备选 TiDB 前的过渡期、或 OB 不可用时的兜底）

**核心：一次分够、映射可变 —— 用「逻辑桶 + 映射表」替代「取模 rehash」。**

```
逻辑桶数 B = 2048（固定，写死在分片算法里，永不改变）
slot = crc32(user_id) % 2048          ← 永远不变，数据永不重算哈希

物理片数 P = 1024（P1 稳态，16 库 × 每库 64 表） → 可降到 512/256（只改映射，不改哈希）
映射表 bucket_map(slot → physical_shard)，存配置中心，原子热更
稳态：2 个桶 → 1 个物理片（1024 片 × 2 桶 = 2048）
缩容 1024 → 512 片：每片接收 2 个桶（桶翻倍到 1 片），仅迁移被挪动的桶

注意：桶数(2048) > 物理片数(1024) 的意义 —— 扩容时若需"更细粒度"，可把 1 片拆成 2 片
（各承接 1 个桶）；反之若要**扩容物理片**（如 1024 → 2048），则桶数必须先升到 4096
（重新做一次全量 slot 迁移），因此初始设计时就把桶数取到远超当前片数（建议 8192）。
```

> **桶数建议修正**：为支持"物理片数继续翻倍"，桶数应取 **8192**（而非 2048），此时
> `slot = crc32(user_id) % 8192`，初期 1024 物理片 × 8 桶/片，可一路扩容到 8192 片不重算哈希。
> `order_no` 的 4 位槽位段随之改为 **3 位十进制槽位（0000-8191，仍 4 位够用）**，编码规则不变。
> 下文统一按 **桶数 8192** 计算。

| 方案 | 数据迁移量 | 复杂度 | 评价 |
|---|---|---|---|
| 取模 N → 2N | 50%（`i` → `i` 或 `i+N/2`） | 中 | 可用，但每次扩容都要全网双写+校验 |
| **预分桶 8192 → 映射表** | 只迁移被挪动的桶 | 中低 | ✅ **推荐**。哈希恒定，历史数据无需重算；扩容按 8/16 桶粒度渐进 |
| 一致性哈希 | ≈ 1/P | 低 | ❌ 负载不均（热点桶），且虚拟节点再平衡仍需搬数据，收益不明显 |

**MySQL 路线扩容步骤（ShardingSphere-JDBC + 自定义 StandardShardAlgorithm 读映射表）**：
1. 新片上线，`bucket_map` 中目标桶置为 `MIGRATING`，新桶双写（写新片 + 写旧片，旧片为准）。
2. 全量迁移该桶（按 `id` 范围切片，每批 5000 行，限速 2 万行/s），增量通过 binlog 追平。
3. 校验：行数 + `SUM(pay_amount)` + `MAX(id)` 三元一致。
4. 映射表原子切换 `→ NEW_SHARD`，关闭双写，旧桶数据延迟 7 天后删。
5. 每次扩容量（桶数）按 16 的倍数，一轮迁移控制在 4 小时内，全程可回滚。

### 3.4 跨片查询读模型（商家查订单 / 运营查订单 / 财务查订单）

**写模型永远按 `user_id` 分片**（下单是最高频写路径，必须单片事务）。所有非 `user_id` 查询走 **CQRS 读模型**：

```
                    ┌──────────────┐
  订单写入 ────────▶│  order_main  │  分片键 user_id（唯一真值）
       │            └──────┬───────┘
       │                   │ CDC（OB Log Service / Canal，秒级）
       ▼                   ▼
  ┌────────────┐    ┌──────────────────┐    ┌─────────────────┐
  │ 本地消息表  │    │  order_index(ES) │    │order_store_wide │
  └────────────┘    │  运营/客服多条件检索│    │ 商家后台列表/批量 │
                    └────────┬─────────┘    └────────┬────────┘
                             │ order_no + user_id     │ order_no + user_id
                             ▼                        ▼
                     ┌────────────────────────────────────┐
                     │ 按 slot 分组 → 并行回表点查 order_main │  （批量 IN，≤ 50 条/批）
                     └────────────────────────────────────┘
```

**四条查询路径的选型**：

| 查询场景 | 主路径 | 数据模型 | 一致性 | 理由 |
|---|---|---|---|---|
| **买家查自己订单**（最高频，占读 60%） | 直查 | `order_main` by `user_id`（缓存 1 min，主动失效） | 强 | 分片键命中，单片，P99 < 5 ms |
| **商家查订单**（`store_id` + 状态 + 时间 + 排序分页） | **宽表** | 新增 `order_store_wide`（分片键 `store_id`），冗余 `user_id`/`order_no`/金额/状态/物流单号 | 最终一致 3～5 s | 商家后台要**多列排序 + 深分页 + 批量发货**，ES 深翻页差、回表 N 次更差；宽表单片内 `ORDER BY created_at DESC LIMIT 50` 直接出 |
| **运营/客服/风控查订单**（关键词、金额区间、手机号、任意组合） | **ES 索引** | `admin-search` 的 `order_index`，命中 `order_no` + `user_id` → 回表点查详情 | 最终一致 3～5 s | 组合条件任意变化，宽表索引跟不上；admin 1.2.1 约束 2 已定此路 |
| **财务/统计/报表**（GMV、类目、地域聚合） | **离线数仓** | CDC → Kafka → ClickHouse/Doris，T+1 | T+1 | 禁止跨片 `SUM()` 进在线链路（admin 1.2.1 约束 2） |

**回表点查的分组算法**（避免散射全片）：
```java
// ES/宽表 返回结果已带 order_no（含 slot）与 user_id
Map<Integer, List<Long>> bySlot = results.stream()
    .collect(groupingBy(r -> Integer.parseInt(r.orderNo.substring(14, 18)),
                         mapping(OrderMain::getId, toList())));
// 每个 slot 一条 SELECT ... WHERE id IN (...)，并行执行，超时 200ms，失败降级"仅展示索引字段"
bySlot.forEach((slot, ids) -> futures.add(pool.submit(() -> loadFromShard(slot, ids))));
```

**明确禁止（写入编码规约）**：
1. 无分片键的 `SELECT ... WHERE store_id=?` 直连 `order_main` —— 1024/2048 分片散射，禁止进入在线链路。
2. 跨片 `JOIN`（`order_item` 已同片，其余一律禁止）。
3. 跨片 `UPDATE` 批量操作（商家批量发货必须按宽表取 `user_id` → 分组 → 分片内批量更新，每片一条 `UPDATE ... WHERE id IN (...)`）。
4. 跨片聚合 `COUNT/SUM` —— 一律走离线。

**宽表 vs 窄索引 vs ES 的量化对比**（100 亿单/年，商家列表页）：

| 方案 | 单页成本 | 一致性 | 额外存储 | 结论 |
|---|---|---|---:|---|
| ES 回表 | 1 次 ES + 5～20 次点查 | 3～5 s | 24 TB | 适合检索，不适合商家列表 |
| 窄异构索引表（`store_id,created_at,order_no,user_id,status`） | 1 次索引查 + 20 次点查 | 3～5 s | 2 TB | 省空间但仍要回表 |
| **宽表 `order_store_wide`** | **1 次查询** | 3～5 s | 6 TB | ✅ 商家场景选它 |

## 4. 冷热分离与归档

### 4.1 三层模型

| 层 | 数据范围 | 存放 | 副本 | 容量（物理） | 查询 SLA |
|---|---|---|---:|---:|---|
| **在线库** | 订单/售后/支付 **0～12 个月**；用户/商品/库存主数据全量 | OB 在线核心集群 | 3 | ≈119 TB | P99 < 20 ms |
| **历史库** | 订单/售后/支付 **13～36 个月**；积分流水 4～12 个月 | OB 独立租户/独立集群（同分区规则，2048 分区） | 2 | ≈74 TB | P99 < 100 ms |
| **归档库** | **> 36 个月** | Parquet on OSS（ZSTD）+ 分区目录表 + Doris 外表索引 | 1 + 跨机房复制 | ≈10 TB | P99 < 3 s（产品明示"历史订单查询较慢"） |

> 与 `admin-backend.md` 12.3.1 现有口径的**修订**：原文"订单 1 年后 → HBase、库存流水 1 年后 → HBase"。**HBase 改为 OB 历史库 + OSS Parquet**，理由：① 引入 HBase 等于多一套集群与运维（RowKey 设计、Region 热点、GC）；② OB 历史库复用同一套 SQL 与连接，业务查询代码零分叉；③ 富文本/冷数据 Parquet 成本是 HBase 的 1/5。**此修订需回写 admin 12.3。**

### 4.2 归档任务设计

```
┌────────────────────────────────────────────────────────────────────┐
│ 归档调度（每日 02:00，低峰；用分布式任务分片，按 slot 分派）              │
│ 1) 取水位：archive_watermark(table, slot, month, last_id, status)   │
│ 2) 选批： WHERE created_at < :cutoff AND id > :last_id              │
│          ORDER BY id LIMIT 5000        （走主键，不扫二级索引）        │
│ 3) 写入历史库（同 slot 分区，INSERT ... 批量 1000 行/事务）            │
│ 4) 校验： 行数 + SUM(pay_amount) + MAX(id) 三元一致，不一致则重试/告警   │
│ 5) 删除在线： 分区方案 → EXCHANGE PARTITION 后 DROP（秒级）            │
│              行方案   → DELETE ... WHERE id BETWEEN ? AND ?（限速 2 万行/s）│
│ 6) 落水位： status=done，断点续传                                     │
│ 7) 对账： 归档前后全量行数守恒（昨日 online + archived = today online） │
└────────────────────────────────────────────────────────────────────┘
```

| 设计点 | 取值 |
|---|---|
| 批量大小 | 5000 行/批，1000 行/事务，单事务 ≤ 500 ms，**不阻塞在线写** |
| 限速 | 全局 ≤ 2 万行/s；只在 02:00～06:00 运行，超过则自动挂起 |
| 幂等 | 水位表 + `INSERT IGNORE`（历史库 `uk_order_no` 片内生效），重复归档无副作用 |
| 校验 | 行数守恒 + 金额守恒（`SUM(pay_amount)` 分桶比对）+ 抽样 1000 行 MD5 |
| 失败处理 | 单 slot 失败不影响其他 slot；连续 3 天失败 → P2 告警 + 人工 |
| 并发控制 | 与在线 DDL/大促错峰；归档期间只读锁该月分区的 DELETE（分区方案无锁） |
| 软删除订单 | `order_main.deleted=1` 的行**一并归档**，归档库保留 `deleted` 标记 |
| 敏感字段 | 归档时 `receiver_mobile` 降为密文不降密；归档库访问走审计（对齐 12.2 策略） |

**对 admin 12.3.2 现有实现的否定**：
```java
List<Order> o = orderMapper.selectBeforeDate(oneYearAgo);   // ❌ 全表扫描，100 亿行必死
orderMapper.deleteBeforeDate(oneYearAgo);                    // ❌ 单事务大删除，锁表 + binlog 爆炸
```
必须替换为上述「水位 + 5000 行分批 + 分区 DROP」实现。这是**必改项**（§7）。

### 4.3 历史订单查询链路

```
用户/客服/商家查询 order_no
   │
```

## 5. 跨服务数据一致性

### 5.1 分布式事务选型（按优先级，高 → 低）

| 优先级 | 方案 | 适用场景 | 具体表/服务 | 性能成本 |
|---|---|---|---|---|
| **P0** | **同分片本地 ACID** | 同一 `user_id` 分片内的多表写 | `order_main` + `order_item` + `payment_order` + `miniprogram_order_extra` + `order_status_log` **必须同片同事务** | 1 次事务提交，5～15 ms |
| **P1** | **本地消息表（Outbox）+ MQ** | 跨服务、可异步、默认方案 | 新增 `outbox_message(id, biz_type, biz_no, payload, status, retry, next_retry_at)` **按 `user_id` 同片**；CDC/RabbitMQ confirm 后置 `sent` | 提交 1 次 + 异步投递 |
| **P2** | **TCC** | **仅资金类**：余额支付、券冻结、积分扣减、库存预占的强资源回补 | `payment_order` 扣款、`user_coupon` 冻结、`admin_inventory` 预占；Try 期冻结 → Confirm/Cancel 幂等 | Try 1 RT + Confirm 异步，约 2× P0 |
| **P3** | **Saga 编排** | 下单长链路（建单 → 预占库存 → 冻券 → 扣积分 → 通知） | 编排器状态存 `saga_instance`（按 `user_id` 分片）；每步失败执行补偿 | 全异步，秒级收敛 |
| **P4** | **对账兜底** | 所有链路 | §5.2 | T+1 |

**明确不用的方案**：

| 方案 | 不用的原因 |
|---|---|
| **Seata AT 模式** | 全局锁 + undo log + 回查，单事务 RT 3～10 倍、吞吐下降 60%+。**50 万/秒下单链路禁用**。仅允许管理端低频操作（结算重算、批量审核）使用 |
| **XA/2PC 跨片** | OB 内部已是 2PC，但跨服务 XA 覆盖面广、超时重试放大，禁止业务层显式 XA |
| **强同步多表跨片单事务** | 把 `product_sku.stock` 更新放进订单事务 → 跨 `spu_id` 分片 → 全局锁热点 SKU，秒级退化。库存必须走 Redis 预扣 + 异步落库（miniprogram 3.5.3 已定） |
| **RabbitMQ 事务消息** | RabbitMQ **无事务消息**（RocketMQ 才有）→ 只能用本地消息表补偿，这点必须在方案评审时明确 |

### 5.2 对账兜底（四层）

| 层 | 频率 | 比对内容 | 发现差异 | SLA |
|---|---|---|---|---|
| **L1 业务内对账** | 每 5 分钟 | 订单状态 vs 库存冻结量 vs 券核销数 vs 积分流水 | 自动补偿重跑 3 次 → 仍失败则 P1 告警 | 收敛 ≤ 30 min |
| **L2 资金对账** | 每小时 | `payment_order` vs 渠道账单（微信/支付宝/抖音）vs 账户流水 | 写 `recon_diff(order_no, type, left_amt, right_amt, status, retry)`，人工审核 | 收敛 ≤ 24 h |
| **L3 财务结算对账** | T+1 | `admin_reconciliation_*` vs `admin_settlement_*` vs 订单明细 | 差异单进入 `admin-finance` 工作台 | 收敛 ≤ 72 h |
| **L4 归档对账** | T+1 | 归档前后行数/金额守恒 | 重跑归档批次 | 收敛 ≤ 48 h |

**差异表 `recon_diff` 设计**：`id`(雪花)、`diff_no`、`biz_type`(order/pay/refund/settle/archive)、`biz_no`、`left_src`/`right_src`、`left_amt`/`right_amt`、`diff_amt`、`status`(0待处理/1重试中/2已补偿/3人工处理/4确认无损)、`handler`、`handled_at`、`created_at`。按 `biz_no` 哈希分片，与被对账域同片。

### 5.3 最终一致性约定

| 项 | 约定 |
|---|---|
| 收敛目标 | 99.99% 的跨服务状态在 **5 秒**内收敛；0.01% 由 L1/L2 对账在 24 h 内修复 |
| 消息可靠性 | 发送端：本地消息表落库（同事务）→ 异步投递 → RabbitMQ `confirm` → 标记 `sent`；消费端 `basic_ack` 在**业务事务提交后** |
| 消费幂等 | Redis `SETNX mp:consume:{messageId}` (TTL 48 h) + 去重表唯一键（与 `admin_message_dedup` 同构，全局按 `message_id` 哈希分片） |
| 重试 | 指数退避 1s/5s/30s/5m/30m，5 次后进死信队列 → 人工工作台（admin 1.1.2 已定） |
| 降级边界 | 资金与状态变更类（改价、退款、结算、打款）**禁止降级**，失败显式报错留痕（admin 1.1.2） |
| 状态推进 | 一律 CAS 条件更新（`UPDATE payment_order SET status='paid' WHERE order_id=? AND status='pending'`），受影响行 0 行 = 已处理（miniprogram 8.1.4 已定） |
| 可观测 | 每条事件带 `messageId` + `traceId`；告警指标：outbox 堆积 > 10 万、消费延迟 > 60 s、`recon_diff` 增量 > 100/h |

## 6. 技术上限（本方案的物理天花板）

### 6.1 上限公式

```
写上限   = (节点数 / 副本数) × 单节点有效行写能力(2～3 万行/s，含二级索引与 2PC 提交)
读上限   = 节点数 × 单节点点查能力(3～5 万 QPS)
容量上限 = 节点数 × 磁盘(8TB) × 可用率(70%) / 副本数 / 压缩比(0.55)
应用层读 = 读上限 × (1 / (1 - 缓存命中率))
分区上限 = 单表 8192 分区 × 单分区 5000 万行 = 4096 亿行/表
```

### 6.2 本方案（42 observer，3 Zone × 14）的能力上限

| 维度 | 上限 | 当前需求 | 水位 | 说明 |
|---|---:|---:|---:|---|
| **在线数据容量** | 142 TB 逻辑（42 × 5.6 ÷ 3 ÷ 0.55，3 副本 × 0.55 压缩） | 71.9 TB | **51%** | 见 §6.1 公式 |
| **持续行写入** | 35 万行/s（42/3 × 2.5 万 × 1.4 批量增益 ≈ 49 万行/s 峰值） | 削峰后 20～40 万行/s | **82%（偏紧）** | 双 11 需提前把批量写打开 |
| **同步订单事务** | **≈ 7 万单/秒**（35 万行/s ÷ 4.6 行/单） | 常态 317 单/s，双 11 瞬时 50 万单/s | 常态 0.5% | **50 万单/秒同步落库不可行**，必须异步削峰 |
| **异步批量落库** | **≈ 10 万单/秒**（批量 1000 行/事务，写放大下降） | 削峰后峰值 ≈ 5～10 万单/s | **100%（临界）** | 见下方"超出路径" |
| **点查读 QPS** | 168 万（42 × 4 万） | 15～25 万（缓存命中 95% 后） | **15%** | 读不是瓶颈，**缓存命中率才是** |
| **应用层读 QPS** | 168 万 ÷ (1−0.95) = **3360 万 QPS 理论值** | 500 万 | **15%** | 但缓存命中掉到 90% 时 DB 需 50 万 → 仍安全 |
| **订单总行数（在线）** | 142 TB ÷ 500 B = **2840 亿行** | 100 亿/年 | 28 年 | 实际靠归档只放 1 年，远不到上限 |
| **单表行数** | 8192 分区 × 5000 万 = **4096 亿行** | 100 亿/年 | 41 年 | 分区数是硬约束，需监控 |
| **单分区行数** | **5000 万**（DDL/迁移/备份粒度红线） | 488 万/年（2048 分区） | **10%** | 超 1500 万触发 split |
| **MySQL 非核心** | 单库 3～5 万写 TPS、单表 5000 万 | 非核心写 < 2000 TPS | 40% | 够用 |
| **ES** | 单集群 100 亿文档量级 | 订单索引 100 亿文档 | 100% | **需要 2～3 个 ES 集群**（订单/商品/日志分集群） |
| **Redis** | 单集群 4 TB 内存、80 万 QPS | 4 TB / 100 万 QPS | 25% | 分片数 ≥ 200，预留 3 倍 |

### 6.3 超出上限需要什么

| 触发信号 | 阈值 | 需要引入的能力 |
|---|---|---|
| **写超过 40 万行/s 持续 5 min** | 集群 CPU > 70% | ① 强化异步削峰（下单返回 `orderToken`，DB 落库延迟到 10～60 s 批量窗口）；② 打开批量写（1000 行/事务）；③ **仍不够 → 按 `user_id` 高位拆成 2～4 个 OB 集群**，网关层做「集群路由表」（slot → 集群），这相当于把 §3.3.2 预分桶方案上移到集群粒度；④ 极限（同步 50 万单/s）需 300+ 节点，**不可行，必须放弃同步语义** |
| **读超过 168 万点查/s** | 缓存命中 < 93% | ① Redis 扩分片（成本最低）；② OB 只读副本（Read-only Zone）；③ 把订单列表/搜索类读迁到 ES/宽表；④ 本地缓存（Caffeine）兜热点 |
| **在线数据 > 142 TB** | 磁盘水位 > 65% | ① 提前归档（在线保留期 12 → 9 个月）；② OB 冷数据下沉对象存储（4.x 支持存储分层，按所选版本确认）；③ 加节点（横向扩容，无 rehash） |
| **单表分区 > 4096** | 分区数 8192 的 50% | 按年拆表（`order_main_2026`），路由层加年份位；或提高单分区到 8000 万（牺牲 DDL 粒度） |
| **行为数据 > 500 TB** | CH 集群成本失控 | 保留期 30 → 14 天 + 更激进降采样（明细 7 天、聚合 90 天）+ 纯对象存储归档 |
| **跨机房/全球化** | — | OB 三机房五副本；或按地域拆集群 + 订单归因路由 |
| **订单 > 500 亿/年（口径变化）** | 单年 5 倍增长 | 分区 2048 → 8192 + 在线归档期缩短 + 集群翻倍；同时重新评审 §1 全部测算 |
| **单点故障域过大** | 单 Zone 故障 = 33% 数据不可写 | 三 Zone 五副本（成本 +67%）或跨机房单元化 |

| 数据迁移 | 引入 OB OMS/obloader 或 CDC 工具链（§8） |

## 8. 落地路径（初期单库 + 逻辑分表 → OceanBase 水平扩容）

### 8.1 四个阶段

| 阶段 | 业务规模 | 存储形态 | 关键动作 |
|---|---|---|---|
| **P0 单库逻辑分表** | 0～100 万 DAU | MySQL 8.0（1 主 2 从）+ `order_main_YYYYMM` 按月逻辑分表 + ShardingSphere-JDBC（**只路由不切库**）+ Redis + ES | 全量 DDL 按 §7 修订落地（雪花 ID、`order_no` 编码、同片约束、detail 外置）。**此时就把 §3.2/§3.5 的编码规则做对**，否则后期无法无损扩容 |
| **P1 分库分表（过渡）** | 100 万～1000 万 DAU | `user_id` 分 16 库 × 每库 64 表 = 1024 片（单片/年 976 万行 ✅）；**停止按月物理分表**（否则 12288 张表过碎），归档改为 `created_at` 索引 + 分批删除 | 预分桶 **8192 桶** + 映射表（§3.3.2，桶数远超片数，后续扩容不用重算哈希），保证 P2 迁移时**哈希不变、数据不用重算** |
| **P2 OceanBase 在线** | 1000 万～3 亿 DAU | OB 3 Zone × 14 observer，`order_main` 单表 2048 分区 | 见 §8.2 触发条件与迁移步骤 |
| **P3 分层与自治** | 3 亿 DAU / 1 亿在线 | OB 在线 + OB 历史库 + OSS 归档 + CH/Doris 行为层；分区自动 split | 冷热分层全量上线，ES 双集群，埋点降采样 |

### 8.2 触发迁移到 OceanBase 的硬条件（满足任一即启动）

| # | 触发条件 | 阈值 | 现象 |
|---|---|---|---|
| 1 | **写 TPS** | 订单写持续 > 2 万 TPS 或峰值 > 5 万 TPS | 主从延迟 > 5 s，下单超时率上升 |
| 2 | **单片行数** | 任一物理分片 > **3000 万行**（红线 5000 万的 60%） | DDL/备份窗口 > 2 h |
| 3 | **容量/磁盘** | 单实例磁盘 > 60%，或总容量 > 8 TB | 备份失败、binlog 空间告警 |
| 4 | **扩容窗口** | 需要的扩容操作 > 2 h 或需要停写 | 业务方拒绝停写窗口 |
| 5 | **跨片查询占比** | 线上跨片散射查询 > 0.5% 的请求量 | P99 > 500 ms |
| 6 | **DBA 人力** | 分库分表运维 > 2 人全职 | 非核心需求被阻塞 |
| 7 | **业务目标** | 明确立项"双 11 承接 50 万/秒" | MySQL 分片无双 11 保底 |

> **建议**：不要等 7 个条件全满足。**条件 1 + 2 同时出现即启动**，因为 P2 迁移周期需要 6～10 周，晚了会撞上大促封网。

### 8.3 P1 → P2 迁移步骤（7 步，全程可回滚）

| 步骤 | 动作 | 工具 | 校验 | 回滚 |
|---|---|---|---|---|
| ① 评估与选型 | Schema 兼容性扫描（`AUTO_INCREMENT`、字符集、JSON、`DATETIME` 默认值、存储过程、触发器——OB 兼容但需逐项过）、SQL 兼容扫描 | OB 兼容性评估工具 | 100% SQL 通过 | — |
| ② 搭建 OB 集群 | 3 Zone × 14 observer，创建租户（CPU/内存配额 = 生产 1.2 倍），建库建表（分区表） | OCP / OBD | 租户连通、TPC-C 基准达标 | 无影响 |
| ③ 全量迁移 | 历史数据导入（先冷数据、后热数据），分批次：非核心表 → 用户/商品 → 订单（只迁在线 12 个月） | OMS / obloader | **行数 + 金额守恒**（分表 `COUNT(*)` + `SUM(pay_amount)` 逐片比对） | 删除 OB 数据 |
| ④ 增量同步 + 双写 | 开启 binlog 增量同步；应用层双写（**MySQL 为准**，OB 写失败不阻塞），同步延迟监控 < 1 s | CDC（Canal/DataX/OMS） | 延迟、失败率、抽样比对 1000 行/分钟 | 关双写开关（配置中心） |
| ⑤ 灰度读 | 按 `user_id` 哈希 1% → 5% → 20% → 50% → 100% 读切 OB，比对双读结果 | 网关/服务内路由开关 | 错读率 < 0.01%，P99 不劣化 > 10% | 读开关回切 MySQL |
| ⑥ 灰度写 | 5% → 50% → 100% 写切 OB（**MySQL 停写**后按反向做第二轮比对），期间 MySQL 转为灾备只读 | 同上 | 双写差异 = 0，连续 7 天 | 写开关回切 MySQL（必须在双写期内完成） |
| ⑦ 收尾 | 下线 ShardingSphere 分片配置、清理双写代码、MySQL 转冷备 30 天后释放；`archive_watermark` 归档任务切到 OB 分区 | — | 全链路回归 + 一次归档演练 + 一次故障演练（杀 Zone） | 30 天内 MySQL 数据保留可回切 |

**P2 后的扩容（不再有 rehash）**：
```
触发：单分区 > 1500 万行 / 节点 CPU > 60% / 磁盘 > 65%
动作：在线分区分裂（2048 → 4096 分区） + OCP 自动负载均衡
限速：≤ 50 MB/s，避开 20:00-24:00
应用：零变更
```

### 8.4 阶段性验收指标

| 阶段 | 验收 |
|---|---|
| P0 | 单表 5000 万内；`order_no` 唯一性压测 1000 万次无重复；缓存命中 ≥ 93% |
| P1 | 1024 分片迁移演练 4 h 内完成 1 片；跨片查询占比 < 0.5%；主从延迟 < 1 s |
| P2 | 混沌演练（杀 1 Zone）写可用；50 万单/s 削峰 10 min 压测通过（DB 落库 ≤ 10 万单/s，队列不爆）；归档 30 亿行/夜 达标 |
| P3 | 全量存储落在 §1.6 预算 ±15%；在线水位 ≤ 65%；历史订单 3 秒内可查 |
