# 亿级架构总索引

> **目标**：在技术上支撑 **1 亿同时在线用户**（≈3 亿 DAU / 5 亿 MAU）的电商平台。
> **范围**：架构设计（10 份专题文档）。硬件与运维只做一份 `10-ops-runbook.md`。
> **与业务计划的关系**：`../plans/` 下的 10 份业务计划定义"做什么"，本文档集定义"怎么扛住量"。两者通过服务名、表名、事件名、接口契约对齐。

| DAU / MAU | 3 亿 / 5 亿 | |
| 客户端 HTTP（含 CDN 边缘） | 2000 万 QPS | 05 号漏斗起点 |
| CDN 边缘命中 | 1502 万 QPS（75.1%） | |
| 回源 / 直连 | ≈498 万 QPS | |
| 应用对外 | ≈423 万 QPS（05 号网关短路后下发值） | **入口总 QPS 规划上限取 630 万（08 号），压测目标 756 万**，见 00-conflict-register 容量总表第 ⑤ 行 |
| 内部 RPC | ≈890 万（05）~1000 万（07，F≈4.6） | **规划取 09 号上限 3,300 万（F≈5）**，见 00-conflict-register C10-f |

| 订单创建峰值 | 50 万笔/秒 | **同步落库硬天花板 7 万单/s（02 号），必须异步削峰到 10 万批量落库** |
| 消息峰值 | 300 万条/秒（设计值 350 万） | 04 号双路径交叉验证 |
| 长连接 | 7000 万（70% 保持率） | |
| 可用性 | 99.99%（52.56 min/年） | 08 号六层预算分解为 47 min，缓冲 10.6% |
| RPO / RTO | RPO=0（有条件）/ RTO<30s | 条件见 08 号 §3.2 |

**技术基线**：Spring Cloud Alibaba（Nacos / Sentinel）+ Dubbo3 Triple & gRPC + RocketMQ 5.x + OceanBase（TiDB 备选）+ Redis Cluster + Caffeine + Elasticsearch + K8s。

**演进原则（01 号裁决）**：`plans/` 现有 10 份业务计划写的是 MySQL + RabbitMQ + ShardingSphere。**P0/P1 阶段不迁移**，P2 阶段一次性迁，避免同期改两个变量。

## 3. 各文档的"技术上限"汇总（诚实结论）

超限不是加机器能解决的，先看这里：

| 约束 | 上限 | 出处 |
|---|---|---|
| 同步订单事务 | **7 万单/s**（需异步削峰至 10 万批量） | 02 |
| MySQL 分片运维 | 2000 分片 | 09 |
| RabbitMQ 单集群 | 5 万 msg/s（需求 75~150 万）→ **必须换** | 04 / 07 / 09 |
| RocketMQ 域集群 | 350 万条/s 需 4~6 集群 ≈175 台；>1000 万才自研 | 04 |
| Redis 集群 | 500 节点 / 3000 万 QPS（余量 7.7 倍，真天花板是 L1 命中率） | 03 |
| ES 搜索 | 300~530 节点，按核采购不经济 → 4 个自研触发信号 | 06 |
| Seata AT | **2000 TPS**（全局锁 3~10ms） | 07 |
| 入口 HTTP | 1000 万 QPS（卡在全局 Nonce/日志总线/Nacos 扇出） | 05 |
| 长连接 | 1.5 亿（卡在 VIP 新建连接） | 05 |
| Sentinel 集群流控 | 单机 1~2 万 check/s → 只用于秒杀/领券 | 05 |
| **第三方支付配额** | **3000~10000/s vs 需求 50 万/s → 必须排队削峰** | 09 |
| 雪花 ID 单元数 | 硬上限 16 个单元（4 位单元 + 6 位节点） | 08 |
| 单元数舒适上限 | 8（N² 跨单元对） | 08 |
| 跨城物理延迟 | 20~30ms（京沪） | 08 |
| 单地域 vCPU | 5~8 万 → 超 5000 万在线必须异地多活 | 09 |

**组件崩塌顺序**（05 号 §8）：回源带宽 → Redis → MySQL 读 → 秒杀配额。

## 5. 与业务计划的对接

- **服务命名**：以仓库实际为准 —— `core-product`（非 core-item）、`core-payment`（非 core-pay），10 个 `core-*` + 21 个 `admin-*`。
  ⚠️ `android-frontend.md` 中的 `core-network` / `core-ui` 等是**安卓客户端模块名**，与后端 `core-*` 同名不同物，禁止混淆。
- **改造名单**（01 号 A/B/C 分级）：A 级 7 个必须改造 —— `core-order` / `core-payment` / `core-user` / `core-inventory` / `core-promotion` / `core-risk` / `edge-gateway`；B 级 6 个副本类；C 级 3 个管理端事件汇聚。`edge-gateway`、`unit-router` 为架构层新增命名。
- **事件**：30 个 MQ 事件全部沿用 plans/ 原事件名，新增 `payment.refund` / `inventory.change` / `risk.review` 三个缺失事件（04）。
- **接口契约**：06 号搜索/推荐契约字段一个不改；03 号 Key 规范以 `ios-backend.md` 四段式为唯一真值。
- **唯一事实来源**：支付超时以 `pay_deadline` 字段为准（解决 15min/30min 冲突）。
