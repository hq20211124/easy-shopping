### 1.1 技术选型

| 类别 | 技术方案 | 说明 |

### 1.3 路由设计

```typescript
// 路由设计原则：按模块聚合，支持权限过滤
const routes = [
  { path: '/login', component: Login },
  {
    path: '/',
    component: Layout,
    children: [
      { path: 'dashboard', component: Dashboard, meta: { title: '工作台' } },
      { path: 'goods/*', component: GoodsRoutes },      // 商品子路由
      { path: 'order/*', component: OrderRoutes },      // 订单子路由
      { path: 'stock/*', component: StockRoutes },      // 库存子路由
      { path: 'user/*', component: UserRoutes },        // 会员子路由
      { path: 'marketing/*', component: MarketingRoutes },
      { path: 'finance/*', component: FinanceRoutes },
      { path: 'content/*', component: ContentRoutes },
      { path: 'report/*', component: ReportRoutes },
      { path: 'system/*', component: SystemRoutes },
      { path: 'shop/*', component: ShopRoutes },
      { path: 'message/*', component: MessageRoutes },
      { path: 'service/*', component: ServiceRoutes },
      { path: '403', component: NoPermission },
    ]
  },
  { path: '/404', component: NotFound },
  { path: '*', component: NotFound }   // 兜底 404，防止未匹配路由白屏
];
```

**交互要点：**
- 路由懒加载：`React.lazy()` + `Suspense`，首屏只加载工作台
- 面包屑自动生成：基于路由 `meta.title` 递归生成
- 页签KeepAlive：订单列表等高频页面保持状态，支持多页签切换
- **KeepAlive 实施说明：** React Router v7 无内置页签缓存，需引入 `react-activation`（或自实现组件缓存，注意与 Suspense/懒加载的兼容）；若引入成本过高，降级方案为「列表筛选条件持久化（URL query + Zustand）+ 表单草稿本地缓存」，排期按降级方案评估
- **错误兜底：** 404 / 403 / 500 三类错误页必须实现；全局 `ErrorBoundary` 捕获渲染异常并上报前端监控（Sentry 或自建），避免整页白屏

### 1.4 权限路由

```typescript
// 路由守卫 + 权限过滤（纯函数实现：不修改原始路由配置，避免多次调用产生全局污染）
type RouteMeta = { title?: string; permission?: string | string[] };

const hasPermission = (routePermission: string | string[] | undefined, permissions: string[]): boolean => {
  if (!routePermission) return true;
  return Array.isArray(routePermission)
    ? routePermission.every(p => permissions.includes(p))   // 数组语义：全部满足
    : permissions.includes(routePermission);
};

const filterRoutes = (routes: RouteObject[], permissions: string[]): RouteObject[] =>
  routes.flatMap(route => {
    if (!hasPermission(route.meta?.permission, permissions)) return [];
    if (!route.children?.length) return [route];
    const children = filterRoutes(route.children, permissions);
    // 子路由被过滤为空且父路由自身无权限标识时，父路由一并隐藏
    if (children.length === 0 && !route.meta?.permission) return [];
    return [{ ...route, children }];
  });
```

**技术要点：**
- 登录后获取用户权限列表（菜单权限 + 按钮权限），存入 Zustand
- 路由守卫组件 `<RequireAuth>` 包裹 Layout，校验 Token + 权限
- 403 页面：无权限时展示申请权限引导页

### 1.6 工程化与质量保障

**代码规范与提交：**
- ESLint + Prettier + Husky + lint-staged，commit message 遵循 conventional commits
- TypeScript 开启 `strict: true`，禁止无注释的 `any`；路径别名统一 `@/`

**请求层规范（axios 封装）：**
- 统一响应结构 `{ code, message, data }`，集中处理：401 → 尝试刷新 Token（并发请求进入等待队列，只触发一次刷新，失败则跳登录并保留 redirect 参数）；403 → 立即重新拉取权限；业务错误码统一映射为用户可读文案
- 请求取消：路由切换时通过 AbortController 取消未完成请求；列表搜索防抖 300ms
- 分页与查询边界：`pageSize` 上限 100；时间范围筛选上限 90 天（报表类 1 年）；深分页改用游标分页或引导走导出

**测试策略：**
- 单元测试：Vitest + React Testing Library，核心 hooks/utils 覆盖率 ≥ 70%
- 接口 Mock：MSW 拦截，前后端并行开发，联调前切换真实接口
- E2E：Playwright 覆盖登录、商品发布、订单改价、退款审核等主链路

**环境与发布：**
- 环境变量：dev / staging / prod 三套 `.env.*`，管理 API BaseURL 与功能开关
- 部署：构建产物部署 Nginx，history 路由必须配置 fallback 到 index.html；静态资源指纹 + CDN 缓存策略
- 发布策略：管理端按账号灰度发布，页面可见版本号，便于问题追溯

### 1.7 与买家端及其他端协同

- **共享服务**：管理端复用 `core-product`、`core-price`、`core-promotion`、`core-user`（见 admin-backend.md 1.1.3）。管理端操作（上架、改价、活动生效）通过 MQ 事件同步买家端缓存与 ES 索引，属**最终一致性**，前端需提示"已提交同步，买家端最长 N 分钟生效"，并提供同步状态查询入口
- **枚举与字典一致性**：订单状态、支付方式、退款原因等枚举编码必须与买家端（PC/H5/小程序/iOS/Android）及 admin-backend.md 保持一致，统一从数据字典接口下发，各端禁止自行硬编码（见 12.4）
- **接口契约**：以 OpenAPI（Swagger）文档为唯一契约源，前端用 `openapi-typescript` 生成 TS 类型，避免手写类型漂移
- **推送通道依赖**：消息通知模块（十四）依赖买家端各端通道——微信订阅消息、APNs/FCM、厂商推送通道、短信，模板与通道配置需与买家端各端计划对齐
- **消息协议统一**：客服会话（15.2）中的订单卡片、商品卡片消息格式需与买家端消息协议统一定义，保证同一消息多端渲染一致
- **联调计划**：每阶段末预留联调窗口，优先联调「登录权限 → 商品 → 订单」三条主链路

## 二、登录与权限

### 2.1 登录页

**页面结构：**
- 左右分栏：左侧品牌展示（平台名称、轮播图），右侧登录表单
- 支持账号密码登录、手机验证码登录、扫码登录（企业微信/钉钉）

**关键组件：**
| 组件 | 功能 | 交互 |
|------|------|------|
| LoginForm | 账号密码表单 | 前端校验格式，错误抖动提示 |
| SmsLogin | 短信验证码登录 | 60s 倒计时，防重复发送 |
| QrCodeLogin | 扫码登录 | 轮询（setInterval 3s）或 WebSocket 推送登录状态 |
| CaptchaButton | 图形验证码 | 点击刷新，服务端校验 |

**技术要点：**
- 密码传输依赖 HTTPS 加密，前端不做 RSA 加密（避免密钥管理复杂性，且 HTTPS 已保障传输安全）；生产环境强制 HTTPS，HSTS 头开启
- Token 存储（与 admin-backend.md 2.1.2 对齐）：`accessToken` 存**内存变量**（不落 localStorage/sessionStorage，防 XSS 窃取），业务请求通过 `Authorization: Bearer` 携带；`refreshToken` 存 `httpOnly Cookie`（`Secure; SameSite=Strict`）仅用于刷新接口。若改为纯 Cookie 携带方案，必须配套 CSRF 双提交令牌（自定义 `X-XSRF-TOKEN` 头）并对所有写接口校验 Origin
- 401 处理：Access Token 过期自动调刷新接口，并发请求排队等待、只触发一次刷新，成功后统一重放；刷新失败（过期/已被踢出）清空本地状态跳转登录页并保留 redirect 参数
- 连续 5 次错误锁定账号 15 分钟，锁定状态后端 Redis 缓存；连续失败 3 次后强制图形验证码，防暴力破解
- 会话超时：Token 有效期 2h，refreshToken 有效期 7d；无操作 30min 自动注销——全局活动监听（mousemove/keydown/click）节流 60s 重置计时器，注销时调用后端登出接口将 Token 加入黑名单；刷新页面后计时器重置属预期行为（以后端 Token 失效为最终兜底）
- 多标签页同步：通过 BroadcastChannel 同步登录/登出/被踢事件，任一标签页退出后其余标签页同步失效，避免"旧会话幽灵操作"
- 扫码登录轮询：登录成功、超时（建议 5min）、组件卸载三种场景必须 `clearInterval`，防止幽灵轮询
- 并发登录：支持配置是否允许多端登录，默认单端登录（新登录踢出旧会话，被踢会话下次请求遇 401/黑名单）

### 2.2 RBAC 权限模型

**数据模型：**
```
用户(User) ──< 用户角色 >── 角色(Role) ──< 角色权限 >── 权限(Permission)
                                                    ├── 菜单权限(menu)
                                                    ├── 按钮权限(button)
                                                    └── 数据权限(data scope)
```

**权限粒度：**
- 功能权限：菜单可见性、按钮可操作性
- 数据权限：以后端定义为准（admin-backend.md 2.3：全部 / 本部门 / 本部门及以下 / 仅本人 / 自定义 五档），前端仅控制默认筛选项与入口可见性，**数据隔离一律由后端 SQL 拦截保证**；商家角色（merchant）仅可见本店铺数据（见 十三、店铺管理）
- 字段权限：敏感字段（成本价、利润率、买家身份证、地址）无权限时脱敏展示（如无 `cost:read` 权限时成本价列显示 `****`），以后端下发脱敏数据为主、前端隐藏列为辅，双保险

**关键页面：**
| 页面 | 功能 | 关键组件 |
|------|------|----------|
| 角色管理 | 角色 CRUD、权限分配 | TreeTransfer（树形穿梭框）、PermissionTree |
| 权限点管理 | 权限点注册、分类 | EditableTable |
| 用户角色分配 | 给用户分配角色 | SelectUserModal、RoleCheckbox |

### 2.3 动态菜单

**实现方案：**
- 后端返回用户可访问菜单树（含权限标识）
- 前端 `filterRoutes` 过滤路由表，动态注册路由
- 菜单支持三级：一级模块 → 二级功能 → 三级 Tab

**交互要点：**
- 侧边栏支持折叠/展开，记住用户习惯
- 搜索菜单：快捷键 `Ctrl+K` 唤起命令面板，模糊搜索跳转
- 面包屑 + 页签联动，支持右键关闭其他/左侧/右侧

### 2.4 按钮级权限

**指令式控制：**
```tsx
// 权限指令
<AuthButton code="goods:create">
  <Button type="primary">发布商品</Button>
</AuthButton>

// Hooks 方式
const { hasPermission } = usePermission();
{hasPermission('order:refund') && <RefundButton />}
```

**技术要点：**
- 权限码命名规范：`模块:操作`（如 `product:create`、`product:edit`、`order:export`），编码以后端权限点注册为准（admin-backend.md 2.1.3 使用 `product:*`，前端禁止另造 `goods:*` 一套）
- 权限变更生效策略（与 admin-backend.md 2.1.4 对齐）：管理员调整权限后，后端将该用户 Token 加入黑名单并删除权限缓存；前端每 5 分钟静默刷新权限列表（React Query `refetchInterval`），敏感操作遇 403 时立即强制刷新权限并提示，不依赖 WebSocket 推送（避免状态不一致风险）
- 权限申请闭环：403 引导页支持提交权限申请单（申请角色/权限点 + 理由），进入管理员审批队列，审批结果通过站内信通知申请人
- 隐藏而非禁用：无权限按钮不渲染，避免"点了没反应"
- 权限变更审计：所有权限分配操作记录操作人、时间、变更内容，可追溯

## 四、商品管理

### 4.1 商品列表

**页面结构：**
- 顶部：搜索栏（商品名称、SKU、品牌、类目、状态、价格区间）
- 操作栏：批量操作（上架/下架/删除/修改分类）、导出、新增
- 主表：ProTable，支持列设置、排序、固定列

**关键列：**
- 商品信息（图片 + 标题 + SKU）
- 价格（销售价、划线价、成本价；成本价无 `cost:read` 权限时显示 `****`，见 2.2 字段权限）
- 库存（总库存、各仓库分布）
- 销量（7日/30日）
- 状态（上架/下架/审核中/违规）
- 操作（编辑、复制、查看）

**技术要点：**
- 虚拟滚动：数据量 > 10000 时启用，保证流畅
- 批量操作上限 500 条，超限提示分批（与后端 batch 上限一致，见 admin-backend.md 3.3.3）；后端异步分批返回成功/失败明细，前端展示失败清单并支持按失败原因筛选重试
- 导出：异步导出 + 站内通知下载，防止大文件超时；下载链接需登录态校验 + 有效期（如 24h），导出记录写入操作日志

### 4.2 商品发布/编辑

**页面结构：** 分步表单（基本信息 → 价格库存 → 商品详情 → 物流售后）

| 步骤 | 字段 | 关键组件 |
|------|------|----------|
| 基本信息 | 标题、品牌、类目、属性、主图 | CategoryCascader、ImageUploader、AttrEditor |
| 价格库存 | SKU 表格（规格组合）、价格、库存 | SkuTable（动态行列）、PriceInput |
| 商品详情 | 详情描述、图文详情 | TipTap 富文本、视频上传 |
| 物流售后 | 运费模板、售后政策、发货时间 | SelectTemplate |

**SKU 生成逻辑：**
- 选择规格（颜色 + 尺寸）→ 笛卡尔积自动生成 SKU 表格
- 支持批量设置价格/库存/重量，个别调整
- 规格图上传，图片与 SKU 关联
- 边界：规格组合数超阈值（如 500 个 SKU）时提示拆分商品或精简规格；已产生销量的 SKU 不允许删除（仅停用），价格/库存变更记录操作日志

**富文本安全：**
- TipTap 输出的 HTML 必须由后端做白名单过滤（防存储型 XSS），买家端渲染前二次 sanitize；上传的视频/图片校验格式与大小，禁止内嵌任意脚本

### 4.3 商品审核

**状态对齐：** 审核状态枚举与后端一致（admin-backend.md 3.3.2）：`draft 待提交 → auditing 审核中 → on_shelf 已上架 / rejected 审核拒绝`，前端禁止自造状态值

**页面：**
- 审核列表：待审核/已审核 Tab，显示提交人、时间、审核进度
- 审核详情：左右分栏（左侧商品信息，右侧审核记录 + 操作）；敏感字段（成本价）按 2.2 字段权限脱敏
- 快捷操作：通过/驳回（必填原因）/退回修改；批量审核上限与失败明细反馈同 4.1 批量操作

### 4.4 类目管理

**功能：**
- 三级类目树，支持拖拽排序
- 类目属性模板：不同类目挂载不同属性（如手机有"屏幕尺寸"，服装有"材质"）

### 4.5 品牌管理

### 4.6 批量操作

**功能：**

### 4.7 商品回收站与草稿

**功能（对齐 admin-backend.md 3.1 商品 P1 能力）：**

## 五、订单管理

### 5.1 订单列表

**搜索条件：**
- 订单号、商品名称、买家信息、订单状态、支付状态、下单时间、金额区间
- 高级搜索：收货地址、支付方式、店铺、推广来源

**关键列：**
- 订单信息（订单号 + 下单时间）
- 商品信息（主商品图 + 标题 + SKU + 数量）
- 买家信息（昵称 + 手机号脱敏）
- 金额（商品总额 + 运费 - 优惠 = 实付）
- 状态（待付款/待发货/待收货/已完成/已关闭/退款中）
- 操作（查看、备注、催付）

### 5.2 订单详情

**页面结构：**
- 订单状态时间轴：下单 → 付款 → 发货 → 收货 → 完成
- 左侧：商品清单、金额明细、优惠明细
- 右侧：收货信息、物流轨迹、操作记录
- 底部：订单备注、操作按钮

**关键操作：**
| 操作 | 说明 | 权限 |
|------|------|------|
| 催付 | 发送短信/站内信提醒买家付款 | 客服 |
| 关闭订单 | 超时未付款自动关闭，或手动关闭 | 运营 |
| 修改收货地址 | 发货前可修改，需二次确认 | 客服 |
| 订单备注 | 内部备注，买家不可见 | 全部 |
| 打印面单 | 调用物流服务打印快递单 | 仓库 |
| 拆单 | 按店铺拆分成子订单 | 运营 |

**并发与审计边界：**
- 修改收货地址使用订单版本号乐观锁；买家端在发货前也可自助改地址，两端并发冲突时以后端最新版本为准，提示"地址已被更新，请刷新后重试"
- 修改地址、关闭订单等敏感操作记录操作日志（前后值脱敏），并校验当前状态仍满足操作前提（如改地址必须仍为待发货）

### 5.3 订单状态流转

**状态机（与 admin-backend.md 4.3 对齐，以后端定义为准）：**
```
待付款(unpaid) ──支付成功──► 待发货(paid) ──发货──► 待收货(shipped) ──确认收货──► 已完成(completed)
     │                            │                        │                          │
     └─超时未付款/手动关闭──►        └──────申请退款──► 退款中(refunding)◄────────────────┘
   已取消(cancelled)                                             │
                                            退款完成──► 已退款(refunded)；售后完成──► 已关闭(closed)
```

**技术要点：**
- 状态变更 WebSocket 推送；列表仅做增量更新，新订单插入不打断当前滚动位置，改为顶部提示"有 N 条新订单，点击刷新"
- 状态不可逆：已退款/已关闭为终态；非法流转按钮直接隐藏（以状态机白名单渲染），后端仍做二次校验
- 并发控制：乐观锁（订单版本号）防止重复操作，冲突时提示"状态已变更，请刷新后重试"
- 断线补偿：WebSocket 断线期间的状态变更在重连成功后全量刷新当前列表/详情，避免状态滞后导致误操作

### 5.4 拆单/合单

**拆单场景：**
- 商家拆单：下单时按店铺自动拆分子订单（后端按 `store_id` 分组拆单，见 admin-backend.md 4.4.2）；仓库维度在发货环节处理，管理端按子订单展示发货状态
- 部分发货：支持子订单独立发货、独立退款、独立售后

**合单场景：**
- 同一买家多笔待付款订单，引导合并支付
- 合并边界：仅同一买家、状态均为待付款、且未占用不可叠加优惠（已核销优惠券/积分需先回退）的订单可合并；合并后触发优惠重算（core-price 引擎），重算后实付差异超过阈值（如 1%）需人工确认再继续
- 合并操作记录操作日志，合并后原订单号在详情中可见（父子关系展示）

### 5.5 改价

**功能：**
- 待付款订单支持改价（降价需审批）
- 改价原因必填，记录操作日志（前后金额、操作人、时间）
- 改价后金额校验：不得低于成本价

**边界与风控：**
- 成本价缺失或当前账号无 `cost:read` 权限时，校验降级为"不低于系统配置底价"并提示
- 买家正在支付中的订单不允许改价（需先确认支付单已关闭），防止支付金额与订单金额不一致
- 改价触发优惠、积分、佣金联动重算（core-price），重算差异写入操作日志
- 改价幅度超过阈值（如 20% 或 500 元）自动进入审批流，审批通过后才生效

### 5.6 退款/售后

**页面：**
- 退款列表：退款单号、订单号、退款金额、原因、状态
- 退款详情：买家申请 → 客服审核 → 财务打款 → 完成
- 操作：同意退款/拒绝退款/协商修改

**技术要点：**
- 退款原路返回，支持部分退款；退款完成后联动库存回补（回补到原发货仓）与积分/优惠券退回，回补状态在详情中可见
- 退款金额校验：累计退款不超过订单实付；退款操作与支付渠道回调均需幂等，防止重复打款
- 退款/售后状态与订单状态机对齐（refunding → refunded / closed，见 5.3）

### 6.5 库存流水

**功能：**

### 9.6 财务通用规范

- 金额精度：前端禁止浮点数运算金额，统一以「分」为整数单位传输（或后端返回字符串），展示层统一走 `formatAmount` 工具格式化，防 JS 浮点误差（如 `0.1 + 0.2`）
- 权限隔离：财务模块仅 `finance_manager` / `finance_clerk` 等财务角色可见；佣金、成本、结算金额对非财务角色脱敏
- 导出管控：财务导出需 `finance:export` 权限 + 二次确认，导出文件加操作人水印，下载链接有效期 24h，全部导出行为写入操作日志
- 审批留痕：结算调整、提现审核、保证金扣减等资金操作强制审批流，审批链路（初审/复审人）在详情页可见且不可篡改
- 对账差异：差异订单支持逐笔下钻至订单详情，差异原因需人工标记（渠道手续费/退款时间差/跨账期等）

- 营业执照：统一社会信用代码、有效期

### 13.4 保证金管理

**功能：**
- 保证金缴纳：按类目要求金额，线上支付
- 保证金扣减：违规处罚扣减，需审批
- 保证金退还：店铺关闭后申请退还，审核后原路返回
- 保证金流水：每笔扣减/退还记录

### 13.5 店铺评分

**功能：**
- 评分维度：描述相符、服务态度、物流速度
- 评分统计：综合评分、各维度评分、趋势
- 评分应用：搜索排序权重、活动报名门槛

### 13.6 店铺冻结/关闭

**功能：**

| 异常监控 | Sentry（或自建）采集 JS 异常、接口错误率、白屏，关键链路埋点告警 |

> **容量口径（千万 DAU）：** 本项目目标为 1000 万 DAU / 峰值在线 200 万，网关入口 60 万 QPS 由服务端分摊；管理端为内部 BS 系统，流量占比极小，**不承担入口容量压力**，前端性能只按页面级指标验收（见 17.3）。容量对管理端的实际传导点有二：① 订单峰值 5 万笔/s 时实时看板与订单列表的增量渲染（3.1/5.3，合并时间窗 + 虚拟滚动）；② 大批量导出一律异步化（16.1 ExportButton）。全局容量与可用性口径（P0 99.9% / P1 同城双活 99.95%）以 `plans/00-架构总纲.md` 为准，本文不另行定义。

### 16.4 安全与数据边界规范

- 查询边界：`pageSize` 上限 100；时间范围筛选上限 90 天（报表类 1 年）；深分页改用游标；超限前端拦截并提示
- 上传边界：图片/Excel 限定单文件大小、批量数量与格式白名单，上传后服务端二次校验（防伪造扩展名、内存炸弹）
- 有害输入：富文本后端白名单过滤；搜索/导出关键词不拼接 SQL，全部走参数化接口
- 敏感数据不落地：用户敏感信息不写入 localStorage/sessionStorage；退出登录清空 Zustand、React Query 缓存与内存 Token
- Cookie 防护：任何使用 Cookie 的场景必须 `SameSite=Strict; Secure; httpOnly`，写接口校验 Origin / CSRF 令牌
- 下载安全：异步导出文件、证照图片等下载链接需登录态 + 有效期，过期返回 403 并引导重新申请

## 十八、风险与注意事项

1. **权限安全**：前端权限仅作体验优化，后端必须二次校验
2. **大数据量**：订单/商品表按统一 16 库 64 表水平拆分、单表数据量仍大，需后端分页 + 虚拟滚动（容量口径见 `plans/00-架构总纲.md`）
3. **并发控制**：库存扣减、订单状态变更需分布式锁
4. **幂等性**：支付回调、退款等接口需幂等设计
5. **审计日志**：所有敏感操作（改价、删除、权限变更）必须记录
6. **数据脱敏**：手机号、身份证、地址等敏感信息列表脱敏
7. **兼容性**：管理端仅支持 Chrome/Edge 最新版，但需考虑 1920/1440/1366 分辨率
8. **前端监控**：接入 Sentry（或自建）采集 JS 异常、接口错误率、白屏，登录/改价/退款等关键链路埋点告警
9. **跨端一致性**：订单状态、支付方式、退款原因等枚举与金额单位必须与买家端各端及 admin-backend.md 一致，变更走数据字典中心统一发布（见 1.7、12.4）
10. **金额精度**：前端禁止浮点数运算金额，统一以「分」为整数或字符串处理，展示统一走格式化工具
11. **CSRF/SSRF 防护**：采用 Cookie 存储时必须 SameSite + CSRF 令牌；服务端渲染/回调类接口校验来源，图片/视频代理禁止任意 URL 抓取
12. **最终一致性感知**：管理端改价、上下架通过 MQ 同步买家端缓存存在延迟，客服/运营操作后话术提示"以买家端实际展示为准"，并提供同步状态查询与对账补偿入口（见 1.7）
